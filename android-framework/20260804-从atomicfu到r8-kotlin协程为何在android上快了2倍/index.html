从 atomicfu 到 R8：Kotlin 协程为何在 Android 上快了 2 倍

本文梳理 kotlinx.atomicfu 的实现原理，以及 Android R8 编译器（AGP 9.2.0+）如何在不改业务代码的前提下，将其原子操作的开销砍掉一大半。

背景：协程为什么离不开原子操作

Section titled “背景：协程为什么离不开原子操作”

Kotlin 协程的核心卖点是「轻量、不阻塞线程」。要做到这一点，协程内部大量使用无锁（lock-free）原子操作来管理跨线程的共享状态，而不是用 synchronized 这类会阻塞线程的锁。典型场景有三个：

  1. 状态机转换：每个 Job / 续体（Continuation）都有一个状态字段，在 ACTIVE → COMPLETING → COMPLETED / CANCELLED 之间流转。这些转换可能来自不同线程（A 线程运行、B 线程取消、C 线程取结果），必须用原子操作保证同一时刻只有一个转换成功。
  2. 结构化并发的父子树：父 Job 用一棵无锁树维护子 Job，子协程启动时挂上去、完成时摘下来、父取消时遍历取消全部子节点——增删都是对共享结构的原子修改。
  3. 调度器任务队列：工作线程用原子出队从队列抢任务，避免同一任务被重复执行。

这些原子操作的根基是 compareAndSet（CAS，Compare-And-Swap）：原子地判断「当前值是否等于预期值」，是则改成新值并返回 true，否则什么都不做返回 false。它不需要锁，失败只需乐观重试：

因为协程的每一次启动、挂起、取消、完成背后都藏着好几次 CAS，这套原语的调用频率极高——这正是它后来成为性能瓶颈的根源。

一、kotlinx.atomicfu 做了什么

Section titled “一、kotlinx.atomicfu 做了什么”

kotlinx.atomicfu 是 Kotlin 官方的无锁原子库，提供跨平台（JVM / Native / JS）的 atomic 属性。它在 JVM 平台上的核心思路是：把一个 atomic 属性编译成一个普通的 volatile 字段，并用 AtomicXxxFieldUpdater 对这个字段就地做原子操作。

  • 字段是普通的 volatile 字段，不是 AtomicReference 这类包装对象；
  • updater 是静态的，整个类只创建一次，newUpdater(...) 内部用反射找到字段并做类型/可访问性校验；
  • 原子语义（CAS 等）由 updater 提供，而不靠额外的原子包装类。

atomicfu 还支持多种变换模式：JDK（用 FieldUpdater，本文焦点）、VH（用 VarHandle，更新 JDK 上无每调用反射开销）、LOCKED（用锁兜底）、NATIVE（走 Kotlin/Native 后端）。在 Android/JVM 主流路径上用的是 JDK 模式。

二、为什么用 FieldUpdater 而不是 AtomicReference

Section titled “二、为什么用 FieldUpdater 而不是 AtomicReference”

你可能会问：直接把字段包成 AtomicReference，调用 atomicRef.compareAndSet(...) 不香吗？香在调用点，但贵在内存。

关键差别在对象分配：

  • 方案 A 每创建一个 JobImpl 就多 new 一个 AtomicReference；
  • 协程实例的创建频率极高——每 launch 一次、每个 suspend 函数、每个 LaunchedEffect、每个 CancellableContinuationImpl 都会 new 出来。一个 Compose 界面滚动一下就可能产生成千上万个协程/续体实例；
  • 如果每个都多带一个原子包装对象，分配开销与 GC 压力会显著上升。

因此 atomicfu 做了一个明确的权衡：用「每次调用的反射开销」去换「零每实例分配」。对生命周期极短、数量巨大的协程对象而言，省一个对象往往比省一次反射调用更划算——至少在 R8 介入之前是这样。

五、效果与适用边界

Section titled “五、效果与适用边界”
  • 经 R8 处理后，kotlinx.atomicfu 与显式 AtomicXxxFieldUpdater 的性能追平原生 AtomicReference；
  • Jetpack Compose 微基准中，LaunchedEffect 启动/取消协程提升约 2 倍；
  • 对重度使用协程的 Compose 应用收益最明显；
  • ART 团队还在做 VM 层优化：API 37+ 较新 Android 上通过 JIT 再带来约 15% 协程提升；
  • 启用方式：升级到 AGP 9.2.0+（或直接使用 R8 9.2.0），优化默认开启，业务代码零改动。

六、为什么库不直接用 Unsafe

Section titled “六、为什么库不直接用 Unsafe”

既然最终也是换成 Unsafe，库自己直接调 Unsafe 不就完了？不行，因为 sun.misc.Unsafe 不是公开、可移植的 API：

  • 它不在标准 Java 公共 API 内，跨 JVM / 跨 Android 运行时不一定可用或稳定；
  • 历史上 Android 对 Unsafe 访问有诸多限制。

因此 kotlinx.atomicfu 作为库，坚持使用公开、可移植的 AtomicReferenceFieldUpdater；而 R8 作为编译期优化器，掌握目标运行时的细节，于是在编译期把这层公开 API 调用特化为 Unsafe 偏移访问。职责分离得很干净：库负责可移植，编译器负责针对 Android 提速。 最终效果恰好是「鱼与熊掌兼得」——保留方案 B「不额外分配对象」的好处，又去掉了「每次反射安检」的坏处。

小结

Section titled “小结”
  1. 协程靠无锁原子操作（CAS）管理状态机与父子树，以保证「轻量、不阻塞」；
  2. kotlinx.atomicfu 在 JVM 上用 AtomicReferenceFieldUpdater 对普通 volatile 字段就地做 CAS，避免每实例分配原子包装对象；
  3. FieldUpdater 每次调用都做反射安检，在协程的原子操作高频场景下被放大成显著瓶颈（约 2.7 倍差距）；
  4. R8（AGP 9.2.0+）在编译期把 updater 调用静态替换为 Unsafe 偏移访问，消除每调用反射开销，使协程在 Android 上快约 2 倍；
  5. 库用公开 API 保可移植，编译器用 Unsafe 特化保性能——开发者升级 AGP 即可免费受益。
