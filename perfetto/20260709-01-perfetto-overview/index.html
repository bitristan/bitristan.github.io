Perfetto （一）：一个系统级追踪平台的架构总览

什么是 Perfetto

Section titled “什么是 Perfetto”

Perfetto 是 Google 开源的系统级追踪（tracing）平台，由一系列 SDK、守护进程和离线分析工具组成。它是 Android 操作系统和 Chromium 浏览器的默认追踪系统，在数十亿设备上运行。

Perfetto 不是单一工具。它是一组协同工作的组件：负责采集的守护进程、负责埋点的客户端 SDK、负责离线分析的 SQL 引擎、以及运行在浏览器中的可视化 UI。理解 Perfetto，首先要理解这些组件如何分工，如何协作。

核心组件一览

Section titled “核心组件一览”

在 Android 设备上，Perfetto 以四个守护进程的形式常驻：

守护进程二进制路径职责
traced/system/bin/traced追踪服务，整个系统的核心调度者
traced_probes/system/bin/traced_probes内核级数据源采集（ftrace、/proc、/sys）
heapprofd/system/bin/heapprofd原生堆内存分析器
traced_relay/system/bin/traced_relay多 VM 环境下的数据中继（与 traced 互斥）

traced_relay 和 traced 不能同时运行。在虚拟化环境中，guest VM 运行 traced_relay 将数据中继到 host VM 上的 traced。

此外还有几个关键的非守护进程组件：

  • perfetto CLI（/system/bin/perfetto）：命令行消费者工具，用于发起追踪会话、读回数据。
  • Tracing SDK：客户端库，应用通过它埋点。C++17 实现，运行时开销极低。
  • Trace Processor：离线分析引擎，将 trace 文件载入列式存储，通过 SQL 查询。
  • Perfetto UI：纯客户端 Web 应用（ui.perfetto.dev），在浏览器中运行 Trace Processor 的 WASM 版本。
  • traceconv：格式转换工具，将 Perfetto trace 转换为 Chrome JSON、pprof 等格式。
  • tracebox：全合一二进制，将 traced + traced_probes + perfetto CLI 打包在一起，适合快速抓取 trace 而无需安装守护进程。

这些进程在 Android init.rc 中定义（见 perfetto.rc 和 heapprofd.rc），通过 persist.traced.enable 属性控制启停。traced 启动后监听两个 UNIX 域套接字：traced_consumer（供消费者连接）和 traced_producer（供生产者连接）。heapprofd 则有独立的 heapprofd 套接字。

Producer-Service-Consumer：三方模型

Section titled “Producer-Service-Consumer：三方模型”

Perfetto 的架构建立在一个三方通信模型之上：Producer（生产者）、Service（服务）、Consumer（消费者）。这不是随意的抽象——每一方都有明确的信任边界和职责约束。

Service：traced 守护进程

Section titled “Service：traced 守护进程”

traced 是整个系统的中枢。它是长驻进程（Android 上是系统守护进程），职责包括：

  • 维护注册表：哪些 Producer 连接了、它们提供了哪些数据源。
  • 拥有中央缓冲区：trace 数据最终写入的 ring buffer 由 traced 管理和持有。
  • 会话复用：多个追踪会话可以并发运行，traced 负责将不同会话的数据路由到各自的缓冲区。
  • 配置路由：消费者发来的追踪配置，由 traced 匹配并转发给对应的生产者。
  • 数据搬运：将生产者共享内存中的数据块拷贝到中央缓冲区。

traced 本身不产生任何 trace 数据。它是一个纯粹的调度和路由中心。

Producer：不受信任的数据源

Section titled “Producer：不受信任的数据源”

Producer 是数据的提供者。可以是任何进程——应用进程、系统服务、甚至 traced_probes 自身。

Producer 是不受信任的。它对整个追踪系统一无所知：

  • 不知道有多少消费者连接着。
  • 不知道有多少并发追踪会话。
  • 不知道有哪些其他 Producer 注册了。
  • 不知道其他 Producer 写了什么数据。

每个 Producer 与 traced 之间有：

  • 一个共享内存缓冲区（SMB），默认 256 KB，所有数据源共享。
  • 一个 IPC 通道（UNIX 域套接字）。

Producer 的全部工作就是：注册自己提供的数据源 → 收到启动指令 → 将 trace 数据写入共享内存 → 通知 traced 搬走数据。

Consumer：受信任的会话控制者

Section titled “Consumer：受信任的会话控制者”

Consumer 控制追踪会话的生命周期。它是受信任的——只有特权进程（如 shell 用户的 perfetto CLI、Android 的 system_server、Chrome 的浏览器进程）才能充当 Consumer。

Consumer 的能力：

  • 发送 TraceConfig 配置：缓冲区大小和数量、要启用的数据源、每个数据源的参数、数据源到缓冲区的映射。
  • 启停追踪会话。
  • 读回 trace 数据（流式传输或通过文件描述符）。
  • 查询会话状态和缓冲区使用情况。

Consumer 与 Producer 之间没有直接通信。两者只与 Service 交互。

端到端数据流

Section titled “端到端数据流”

一次完整的追踪会话经历了以下阶段：

阶段一：注册

Section titled “阶段一：注册”
  1. Producer 进程启动后，通过 IPC 连接到 traced。
  2. Producer 调用 RegisterDataSource，声明自己能提供哪些数据源（如 "linux.ftrace"、"track_event"）。
  3. 此时没有任何数据被采集。注册只是声明能力。

阶段二：配置与启动

Section titled “阶段二：配置与启动”
  1. Consumer（如 perfetto CLI）连接到 traced，发送 EnableTracing(TraceConfig)。
  2. traced 根据配置创建中央缓冲区（V1 或 V2 格式，ring buffer 或 stop-when-full 策略）。
  3. traced 遍历配置中的 data_sources，在注册表中查找匹配的 Producer。
  4. 对每个匹配的 Producer，traced 发送 SetupTracing（每个 Producer 只发一次，附带共享内存 fd 和页大小）和 SetupDataSource（每个数据源发一次，附带该数据源的配置）。
  5. 然后对每个数据源发送 StartDataSource 指令。

阶段三：采集

Section titled “阶段三：采集”
  1. Producer 收到启动指令后，创建 DataSource 实例和 TraceWriter（通常每个线程一个）。
  2. TraceWriter 通过 ProtoZero 库直接将 protobuf 编码的 TracePacket 写入共享内存的 chunk 中。
  3. 当 chunk 写满或数据包完成时，SharedMemoryArbiter 异步发送 CommitDataRequest IPC 给 traced。这个 IPC 不阻塞写入线程——arbiter 会在内部累积多个 commit 请求，批量发送以减少 IPC 开销。
  4. traced 收到请求后，通过原子 CAS 将 chunk 标记为”正在读取”，将数据拷贝到中央缓冲区，然后将 chunk 标记为”空闲”供 Producer 重用。

这个阶段的关键设计：trace 数据本身不走 IPC 通道。数据通过共享内存传递，IPC 只用于控制消息和 chunk 管理。这是 Perfetto 高性能的核心——避免了大数据量的 IPC 拷贝。

阶段四：读回

Section titled “阶段四：读回”
  1. Consumer 发送 Flush 请求，traced 向所有 Producer 广播 Flush 指令。
  2. Producer 提交所有未完成的数据，traced 执行 SMB scraping（扫描共享内存中未提交的 chunk）。
  3. Consumer 发送 DisableTracing 停止采集。
  4. Consumer 发送 ReadBuffers，traced 将中央缓冲区的内容流式传回。
  5. Consumer 将数据写入 .perfetto-trace 文件。

阶段五：离线分析

Section titled “阶段五：离线分析”
  1. 用户在浏览器中打开 ui.perfetto.dev，加载 trace 文件。
  2. UI 中嵌入的 Trace Processor（WASM 版）解析 trace 文件，建立列式存储。
  3. 用户通过 SQL 查询或时间线可视化来分析数据。

共享内存：性能的关键

Section titled “共享内存：性能的关键”

共享内存（Shared Memory Buffer，SMB）是整个追踪快速路径的基础。理解它，就理解了 Perfetto 为什么能做到低开销。

SMB 是 Producer 与 traced 之间共享的一块内存区域，由 traced 在 Producer 连接时创建，通过 UNIX 域套接字的 SCM_RIGHTS 机制将文件描述符传递给 Producer 进程。它的设计约束：

  • 固定大小：默认 256 KB，可通过配置调整，上限 32 MB。
  • ABI 稳定：二进制格式必须保持向后兼容。
  • 所有数据源共享：一个 Producer 的所有数据源共用同一个 SMB。
  • 与中央缓冲区无关：SMB 的大小独立于 trace 文件的大小。

SMB 内部分为两层：Page（页） 和 Chunk（块）。

每页有一个 8 字节的 PageHeader，其中 header_bitmap 是一个 atomic uint32，编码了页的布局（1/2/4/7/14 块划分）和每个 chunk 的状态。chunk 状态通过**原子比较交换（CAS）**在四个状态间转换：Free → BeingWritten → Complete → BeingRead → Free。

这意味着 Producer 和 traced 之间的 chunk 交接完全无锁——两边只通过原子操作协调，不需要互斥量。

ProtoZero：零拷贝序列化

Section titled “ProtoZero：零拷贝序列化”

标准 protobuf 库的序列化过程需要一个中间缓冲区：先序列化到临时 buffer，再拷贝到目标位置。对于每秒可能产生数万个事件的追踪场景，这个额外拷贝是不可接受的。

ProtoZero 是 Perfetto 自研的 protobuf 序列化库，核心思想是直接写入最终目标——也就是 SMB 中的 chunk。它通过 ScatteredStreamWriter 管理不连续的内存片段，当一个 chunk 写满时无缝切换到下一个。

ProtoZero 的一个精巧设计是延迟 size 修补。protobuf 的嵌套消息需要在开头写入长度字段，但写入时最终长度未知。ProtoZero 的做法是：预留 4 字节，继续写入数据，待消息完成后再回头修补长度。如果消息跨越了 chunk 边界，修补需求被记录到 PatchList，通过后续的 CommitDataRequest 由 traced 在中央缓冲区中完成修补。

Trace Processor：SQL 驱动的分析引擎

Section titled “Trace Processor：SQL 驱动的分析引擎”

Trace Processor 是 Perfetto 的离线分析核心。它不运行在采集端——它通常在开发者的工作站或浏览器中运行。

它的数据流水线：

Trace Processor 内嵌 SQLite，通过 vtable API 将自有的列式存储引擎（Dataframe）暴露为 SQL 表。每张表的列带有丰富的元信息（排序状态、是否有重复值、null 策略），查询规划器利用这些信息选择最优算法——例如对排序列使用二分查找，对小值无重复列使用 O(1) 等值查询。

Trace Processor 以插件形式组织功能。内置插件覆盖 ftrace、调度、内存、GPU、Android、Chrome 等领域，每个插件可以注册导入器、SQL 函数、虚拟表、Dataframe。插件之间通过 CRTP 声明依赖，初始化时拓扑排序保证正确的加载顺序。

Perfetto UI：浏览器中的 Trace 查看器

Section titled “Perfetto UI：浏览器中的 Trace 查看器”

Perfetto UI 是一个纯客户端的 TypeScript 单页应用，运行在 ui.perfetto.dev。它没有服务器组件——所有计算都在浏览器中完成。

它的核心技术亮点是将 Trace Processor 编译为 WebAssembly 并在 Web Worker 中运行。启动时，主线程通过 WebAssembly.compileStreaming() 预编译 WASM 模块，然后传递给 Worker。Worker 内部通过 protobuf 编码的 RPC 消息与主线程通信。

UI 采用 Mithril.js（非 React）框架，通过插件架构组织功能。13 个核心插件提供时间线、注释、设置等基础能力，100+ 个用户插件覆盖 Android、Chrome、CPU、GPU、内存、调度等各类 trace 数据的可视化。插件通过 import.meta.glob 自动发现，拓扑排序后初始化。

每个插件在 onTraceLoad 时向 UI 注册 Track（轨道），Track 的渲染逻辑通过 SQL 查询获取数据。例如一个调度 slice Track 会查询 sched_slice 表，一个 counter Track 会查询 counter 表。

构建系统

Section titled “构建系统”

Perfetto 使用 GN（GenerateNinja）+ Ninja 作为主要构建系统，同时支持 Android Soong（Android.bp，约 26000 行，自动生成）和 Bazel（MODULE.bazel）。

四种构建配置：

  • Standalone：独立构建，开发者日常开发模式。
  • Android tree：在 AOSP 中作为系统组件构建。
  • Chromium tree：在 Chromium 中构建。
  • 其他 embedder：如 V8 独立构建。

构建配置通过 gn/perfetto.gni 中的特性开关控制（如 enable_perfetto_platform_services、enable_perfetto_heapprofd、enable_perfetto_traced_perf 等），确保在不同嵌入场景下只编译需要的组件。

ABI 稳定性策略

Section titled “ABI 稳定性策略”

Perfetto 不使用版本号来管理兼容性。它的策略是：

  • Protobuf 天然兼容：TracePacket 和 DataSourceConfig 使用 protobuf 的前向/后向兼容性。新增字段使用新的 field number，旧代码忽略未知字段。
  • Feature flags：新增功能通过可选字段暴露。消费者通过 has_xxx 检测生产者是否支持某功能。
  • 共享内存 ABI 稳定：SMB 的二进制格式（页头、chunk 头）不使用版本号，通过精心设计的字段布局保证向后兼容。

这种策略使得 Android 系统组件可以独立升级——一个新版本的 traced 可以和旧版本的应用进程协作，反之亦然。

代码组织

Section titled “代码组织”

源码树的核心目录：

src/base/ 是所有 C++ 组件共享的基础库，包含任务运行器（TaskRunner）、UNIX 域套接字、管道、事件 fd、flat hash map、字符串工具等。它刻意保持精简，不依赖 Perfetto 的其他模块。

src/tracing/ 实现 SDK 的核心逻辑：TraceWriter（将数据写入 SMB）、SharedMemoryArbiter（管理 chunk 分配和提交）、IPC Producer/Consumer 代理。include/perfetto/tracing/ 则是用户面对的公开 API：TRACE_EVENT 宏、DataSource 模板、Tracing::Initialize 等。

适用场景

Section titled “适用场景”

Perfetto 的设计覆盖了从嵌入式设备到桌面浏览器的广泛场景：

  • Android 应用和平台开发者：追踪启动耗时、掉帧、ANR、内存问题。Perfetto 是 Android 系统内置的追踪基础设施。
  • Chromium 开发者：chrome://tracing 的后端就是 Perfetto。追踪浏览器、V8、Blink 的行为。
  • Linux 内核和系统开发者：作为 ftrace 的用户空间守护进程，可视化调度、系统调用、中断等内核行为。
  • C/C++ 应用开发者：通过 Tracing SDK 在应用中埋点，支持 Linux、macOS、Windows。
  • 性能工程师：分析来自 Linux perf、macOS Instruments、pprof 等多种工具的 trace 数据。

本文小结

Section titled “本文小结”

Perfetto 是一个由多个组件构成的系统级追踪平台。它的核心架构是 Producer-Service-Consumer 三方模型，通过共享内存实现高性能的数据传输，通过 ProtoZero 实现零拷贝序列化，通过 Trace Processor 的列式存储和 SQL 引擎实现灵活的离线分析。
