Perfetto （十三）：Dataframe 列式存储引擎

设计动机

Section titled “设计动机”

Trace Processor 需要存储和查询海量 trace 数据——一次典型的系统 trace 可能包含数百万行事件。传统的行式存储（如 SQLite 的 B-tree）对 trace 分析场景不够高效：大多数查询只涉及少数列，但需要扫描大量行。列式存储使得只读取需要的列，大幅减少 I/O 和内存带宽。

但 Perfetto 没有使用现成的列式数据库引擎——它实现了一个专用的 Dataframe，专门为 trace 数据的访问模式优化：不可变（append-only 后冻结）、列式存储、字节码驱动的查询执行、与 SQLite 虚拟表的深度集成。

类型系统

Section titled “类型系统”

存储类型

Section titled “存储类型”

类型说明典型用途

Uint3232 位无符号整数cpu, priority
Int3232 位有符号整数depth, flags
Int6464 位有符号整数ts, dur, value
Double64 位浮点计数器值
StringStringPool 中的 StringIdname, category

空值类型

Section titled “空值类型”

Nullability TypeSet 定义了 5 种空值处理策略：

类型说明性能特征
NonNull不允许空值零开销
SparseNull用 BitVector 标记哪些行是 NULL只需 1 bit/行的额外空间
SparseNullWithPopcountAlways始终维护 popcount 索引O(1) 跳过 NULL 行，适合查询阶段

DenseNull每行都可能为空，值内联存储用于 overlay 链

排序状态

Section titled “排序状态”

SortState TypeSet 追踪列的有序性：

类型说明
IdSorted列是 ID 且单调递增（行号 = 值）
SetIdSorted列的值集合与 IdSorted 列相同，但顺序不同
Sorted列按非递减排列
Unsorted无序

IdSorted 是最强的排序状态——如果查询条件是 id = 42，可以直接定位第 42 行，O(1) 访问。

列的物理结构

Section titled “列的物理结构”

每列由三层组成：

FlexVector：基础存储

Section titled “FlexVector：基础存储”

FlexVector<T>（src/trace_processor/core/util/flex_vector.h）是一个容量对齐到 64 元素的动态数组：

  • 容量对齐到 64 元素：kCapacityMultiple = 64，所有容量向上对齐到 64 的倍数，减少频繁的 realloc。
  • 1.5 倍增长因子：比 std::vector 的 2 倍更节省内存。
  • 只支持追加：push_back() 和 push_back_multiple() 是主要的写入操作。

Overlay：延迟更新

Section titled “Overlay：延迟更新”

列在创建后是不可变的——但有时需要”更新”列值（例如标记某些行为 NULL）。Overlay 层通过在基础列之上叠加一个稀疏的修改集来实现这一点，避免复制整个列。

SparseNullOverlay 维护一个 BitVector（带 popcount），标记哪些行在 overlay 层有修改。实际修改值存储在 overlay 的值数组中。读取时，先检查 overlay——如果该行有修改就返回 overlay 的值，否则 fallback 到基础列。

多个 overlay 可以嵌套——形成 overlay 链。这使得列可以在查询计划的多个阶段被”修改”而无需复制。

PopcountBitVec

Section titled “PopcountBitVec”

BitVector 使用 popcount（Population Count）指令加速位操作。PackLeft() 将稀疏的 bit 向量压缩为连续存储——popcount 用于快速计算压缩后的索引。Compact() 操作使用 PEXT（Parallel Extract）指令在支持的 CPU 上进一步优化。

查询计划生成

Section titled “查询计划生成”

PlanQuery() 是查询优化的核心。它生成一个字节码序列，执行以下步骤：

1. 过滤器排序

多个过滤器按评估成本排序。选择性高（过滤掉更多行）的过滤器优先执行，减少后续步骤处理的行数：

2. 三阶段过滤

过滤分三个阶段：

  • 阶段一：索引操作。如果过滤器作用于 IdSorted 列且操作是 Eq，直接计算行号（O(1)）。如果作用于 Sorted 列，使用二分查找定位范围。
  • 阶段二：位向量操作。将阶段一的结果与 sparse null 的位向量做 AND/OR 操作，进一步缩小候选集。
  • 阶段三：扫描操作。对剩余的过滤器，逐行扫描候选集。

3. 排序和去重

如果查询包含 ORDER BY 或 DISTINCT：

  • 对 Unsorted 列排序：使用 std::sort。
  • 对 Sorted 列去重：扫描一次，跳过连续重复值。
  • IdSorted 列的 DISTINCT 直接返回所有行（ID 天然唯一）。

字节码执行引擎

Section titled “字节码执行引擎”

查询计划被编译为字节码，由 BytecodeInterpreter 执行。字节码定义在 bytecode_instructions.h，包含约 170+ 个具体操作码（模板实例化后）。核心字节码包括：

字节码说明
InitRange初始化行范围 [0, row_count)
SortedFilter<T, Op>对 Sorted 列做二分查找范围过滤（两个模板参数：存储类型和比较操作）
Uint32SetIdSortedEq对 IdSorted 列做 O(1) 直接定位
LinearFilterEq<T> / NonStringFilter<T,Op> / StringFilter<Op>逐行扫描，评估过滤条件
NullFilter<NullOp>用 BitVector 过滤 NULL 行
TranslateSparseNullIndices / PrefixPopcount将 overlay 的压缩索引翻译为基础列索引
AllocateIndices分配索引缓冲区
StrideCopy / CopyToRowLayout<T, Nullability>复制列数据到结果（两个模板参数）
Distinct去重操作
SortRowLayout排序操作
LimitOffsetIndices限制返回行数

每个字节码是一个不超过 40 字节的结构体（Bytecode，static_assert(sizeof(Bytecode) <= 40)），包含操作码和操作数。查询计划器为每条指令附加代价估算（独立于 Bytecode 结构），用于选择总代价最小的执行计划。

寄存器模型

Section titled “寄存器模型”

字节码操作虚拟寄存器。RegValue 是一个包含 14 种类型的 std::variant，核心类型包括：

  • Range：行范围（b 起始，e 结束）
  • Slab<uint32_t>：索引缓冲区（候选行号）
  • const BitVector*：位向量指针（候选集）
  • StoragePtr：列数据指针（包含 ptr 和 type）

TranslateSparseNullIndices 是最特殊的字节码——它处理 overlay 层的索引翻译。当 overlay 的 BitVector 有 popcount 时，PrefixPopcount 将稀疏索引压缩为连续索引，TranslateSparseNullIndices 将压缩索引翻译回原始行号。

性能特征

Section titled “性能特征”
  1. 列式存储：只读取查询涉及的列，减少内存带宽。
  2. 编译时类型特化：每种列类型组合生成特化代码，无虚函数开销。
  3. 排序感知的查询计划：利用列的排序状态选择最优访问路径。
  4. Overlay 延迟更新：避免修改列时的全量复制。
  5. 字节码执行：比解释执行快，比 JIT 简单。
  6. 容量对齐到 64 元素：FlexVector 的容量向上对齐到 64 元素倍数，减少频繁 realloc。
  7. Popcount 加速：BitVector 的压缩和翻译使用 SIMD 指令。

本文小结

Section titled “本文小结”

Dataframe 是 Trace Processor 的存储核心。它用编译时的类型系统（StorageType × Nullability × SortState）为每种列类型组合生成特化代码。Overlay 层实现了列的延迟更新而无需复制。查询计划通过成本模型选择最优的过滤策略和字节码序列。字节码执行引擎用 40 字节的紧凑指令驱动列式评估。DataframeModule 虚拟表桥接将这一切暴露为 SQL 可查询的表，同时通过约束下推绕过 SQLite 的逐行引擎。
