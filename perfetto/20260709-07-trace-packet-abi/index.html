Perfetto （七）：TracePacket 与 ABI 稳定性

信封模式

Section titled “信封模式”

Perfetto 的 trace 文件是一系列 TracePacket 的线性序列。TracePacket 是所有 trace 数据的统一信封——无论数据来自 ftrace、heapprofd、TrackEvent 还是任何其他数据源，最终都被包装在 TracePacket 中。

oneof data 是信封模式的核心。每个数据源在这个联合体中有一个专用字段。添加新数据源只需新增一个字段——旧的消费者会自动忽略未知字段（标准 protobuf 行为）。

三种字段层级

Section titled “三种字段层级”

TracePacket 的数据字段被注释分为三个层级：

稳定公开 API（track_event、track_descriptor、以及一系列 generic_kernel_* 事件）：这些字段承诺长期稳定，Trace Processor 和 UI 依赖它们的行为。

不稳定/上下文相关字段（ftrace_events、process_tree、chrome_events、profile_packet 等）：这些字段可能在不同时期发生变化。虽然 protobuf 的字段编号不会被回收，但字段内部的结构可能演进。

已废弃字段（process_descriptor、thread_descriptor）：被 track_descriptor 取代，保留字段编号以避免冲突。

无版本号策略

Section titled “无版本号策略”

Perfetto 的 ABI 策略中最重要的决定是：不使用版本号。

trace 文件中没有版本号，IPC 协议中没有版本号，共享内存 ABI 中没有版本号。这个决定的背后逻辑是：在 Android 生态中，traced 作为系统守护进程被冻结在系统镜像中，而应用和工具（如 Chrome、perfetto CLI）可以独立更新。如果使用版本号，每次新增功能都需要协调版本——这在数十亿设备的生态中是不可行的。

替代方案是 protobuf 的前向/后向兼容性 + 功能标志。标准 protobuf 兼容规则保证：新字段可以添加（旧代码忽略），字段不能移除（只标记为 deprecated + reserved），字段编号和类型不能改变。

功能标志协商

Section titled “功能标志协商”

当需要协商行为变化（而非数据格式变化）时，Perfetto 使用功能标志。

DataSourceDescriptor 是 Producer 在注册数据源时提交的描述符，其中包含多个布尔标志：

每个标志独立引入，各自带有时间戳。例如 will_notify_on_stop 在 2018 年 7 月引入（Android P 之后），handles_incremental_state_clear 在之后引入。traced 检查这些标志来了解 Producer 的能力；Producer 通过 QueryCapabilities 了解 traced 的能力。如果对方不支持某个功能，双方优雅降级。

trusted_packet_sequence_id

Section titled “trusted_packet_sequence_id”

trusted_packet_sequence_id 标识一个 Producer + TraceWriter 对。它是服务端分配的——通过 oneof optional_trusted_packet_sequence_id 包装防止 Producer 伪造。

这个 ID 的核心作用是划定增量状态的作用域。所有带有相同 sequence ID 的 packet 形成一个有序序列，序列内的 packet 保证顺序且无间隙。不同序列之间没有顺序保证。

增量状态（InternedData、TracePacketDefaults）在一个序列内累积，跨序列不共享。

增量状态与序列标志

Section titled “增量状态与序列标志”

增量状态是 Perfetto 用来减少重复数据的机制。但引入增量状态后，解析者面临一个问题：如果丢失了定义 interned 数据的 packet，后续引用它的 packet 就无法解析。

sequence_flags 字段解决了这个问题：

SEQ_INCREMENTAL_STATE_CLEARED：Writer 声明从此 packet 开始，将重新发射所有需要的增量数据。之前发射的 InternedData 不再被引用。消费者如果检测到丢包（通过 previous_packet_dropped），应跳过当前序列直到下一个带此标志的 packet。

SEQ_NEEDS_INCREMENTAL_STATE：本 packet 依赖增量状态。如果消费者尚未看到当前序列的 SEQ_INCREMENTAL_STATE_CLEARED，应跳过此 packet。

两个缓解措施：

  1. 定期清除：TraceConfig.IncrementalStateConfig.clear_period_ms 让 Producer 周期性地重新发射增量状态。
  2. 专用缓冲区：将增量状态录制到独立的 target_buffer，减少丢失概率。

TracePacketDefaults

Section titled “TracePacketDefaults”

TracePacketDefaults 是一种减少逐 packet 开销的优化机制。它利用了 trace 事件的常见模式——同一序列中的大量事件共享相同的字段值（如 track UUID、时钟 ID）。

工作方式：一个带有 trace_packet_defaults 和 SEQ_INCREMENTAL_STATE_CLEARED 的 packet 建立新默认值。后续同序列的 packet 继承这些默认值，除非在 packet 中显式覆盖。

TrackEventDefaults 的核心字段是 track_uuid——如果一个序列的所有 TrackEvent 都在同一个 track 上（如所有事件都在同一个线程），track_uuid 只需在 defaults 中设置一次，每个 packet 可以省去这个字段。对于高频事件（每秒数千个），这节省了可观的带宽。

注意 TracePacketDefaults 的字段编号与 TracePacket 的字段编号一一对应（如 timestamp_clock_id = 58 在两者中相同）。这使得消费者可以用统一的方式处理默认值和显式值。

InternedData：字符串去重

Section titled “InternedData：字符串去重”

InternedData 提供序列级别的字符串去重。每个 interned 条目有一个 iid（interning ID），后续 packet 通过 iid 引用而非重复发送字符串。

InternedData 在序列内增量累积。当 SEQ_INCREMENTAL_STATE_CLEARED 被设置时，interned 索引被重置，Writer 会在后续 packet 中重新发射被引用的 interned 数据。

DataSourceConfig 是从 Consumer 的 trace 配置到 Producer 的数据源之间的桥梁：

[lazy = true] 是一个关键设计：它告诉 proto-to-C++ 代码生成器不要递归解析这些字段。traced 核心服务将它们视为不透明的字节 blob，只有对应的 Producer 才需要解析。这防止了数据源特定的代码泄漏到核心服务中。

legacy_config（field 1000）是一个文本格式的逃生舱口——万一未来某个数据源的配置格式需要突破 protobuf 的前向兼容性约束，可以用文本格式传递。

扩展模型：带外数据源

Section titled “扩展模型：带外数据源”

Perfetto 通过 protobuf 的 extensions 机制允许外部项目添加自己的数据类型，无需修改 Perfetto 的上游 proto 定义。

扩展分配管理在 extensions.json 中，CI 强制检查：

扩展的工作流程：

  1. 定义数据 proto（如 acme_data.proto）。
  2. 定义扩展 proto，使用分配的 field number 扩展 TrackEvent。
  3. 在 trace 中嵌入 ExtensionDescriptor packet（携带 FileDescriptorSet），使 Trace Processor 能解析未知扩展。
  4. 也可以通过系统级描述符文件（/etc/tracing_descriptors.gz）或 Extension Server 分发描述符。

这使得 Winscope、蓝牙追踪、ART 堆图、Chrome 专用事件等可以共存于同一 trace 格式中。

静态链接策略

Section titled “静态链接策略”

Perfetto 的 C++ 客户端库只以静态库形式分发。一旦链接，它只依赖 socket 和共享内存的 ABI——这些 ABI 保证稳定。

不提供共享库（.so）的原因：C++ 的 ABI 稳定性（符号修饰、虚表布局、inline 函数）维护成本极高。Perfetto 大量使用模板和 inline 头文件，使得共享库分发不切实际。

一个新的 C 语言 API/ABI（include/perfetto/public/）正在开发中，提供稳定的 C ABI，避免 C++ ABI 的复杂性。

文件级兼容性保证

Section titled “文件级兼容性保证”

Trace 文件的兼容性遵循一个简单的规则：Trace Processor 总是能解析比它旧的 trace 文件。

这是因为 protobuf 的解码器会忽略未知字段，而 Perfetto 保证：

  • 不删除字段（只 reserved）。
  • 不改变字段编号或类型。
  • 新增字段总是可选的。

反向兼容（新版 trace 文件在旧版 Trace Processor 中解析）也部分支持——旧版会忽略未知字段，但可能丢失新数据源的信息。

本文小结

Section titled “本文小结”

Perfetto 的 ABI 稳定性策略建立在 protobuf 的前向/后向兼容性之上，通过功能标志协商行为变化，通过扩展机制允许带外数据源，通过 TracePacketDefaults 和 InternedData 减少逐 packet 开销。整个系统没有版本号——兼容性由 protobuf 的线格式保证，行为变化由功能标志驱动。这个策略使得 Android 系统组件可以独立升级，而不会破坏生态中的其他组件。
