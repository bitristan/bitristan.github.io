Perfetto （四）：ProtoZero 零拷贝序列化

设计动机

Section titled “设计动机”

Perfetto 的每个 trace 事件都是一个 protobuf 编码的 TracePacket。protobuf 提供了强类型和跨语言兼容性，但标准的 libprotobuf 库在追踪场景下存在三个根本性问题：

  1. 两步序列化：libprotobuf 的使用模式是”先设置字段到 C++ 对象 → 再调用 SerializeAsString()”。这要求一个中间对象持有所有字段的副本，产生内存分配和拷贝。
  2. 二进制膨胀：libprotobuf 生成的代码为每个 proto 字段生成独立的成员变量和访问方法。即使只使用了一小部分字段，整个消息类的代码也必须被链接到二进制中，导致 I-cache 压力。
  3. 连续缓冲区假设：libprotobuf 的序列化输出要求连续的目标缓冲区，而 Perfetto 的共享内存由固定大小的 chunk 组成，天然不连续。

ProtoZero 的设计目标是 zero-copy、zero-alloc、zero-syscall 的序列化。它不是通用的 protobuf 库——它专门服务于追踪写入路径，用功能换性能。

核心思路：append-only 序列化

Section titled “核心思路：append-only 序列化”

ProtoZero 与 libprotobuf 的根本区别在于：ProtoZero 生成的类没有字段存储。

关键差异：ProtoZero 的 set_* 方法直接将数据编码到目标缓冲区，没有中间存储。调用 set_int_val(42) 时，protobuf 编码的字节立刻写入共享内存。生成的类不增加任何额外成员——static_assert(sizeof(T) == sizeof(Message)) 确保了这一点。

这带来了三个直接后果：

  • 不可回读：写入后无法再读取字段值，因为根本没有存储。
  • 栈式写入：嵌套消息必须按栈顺序填充——开始写子消息后，必须完成子消息才能回到父消息。
  • 二进制大小与使用量成正比：不调用的 set_* 方法不会产生运行时代码。libprotobuf 的问题——未使用字段的代码也被链接——在这里不存在。

代码生成

Section titled “代码生成”

ProtoZero 的编译器是一个 protoc 插件（src/protozero/protoc_plugin/protozero_plugin.cc）。构建时依赖 libprotobuf 的解析器，但生成的代码运行时零依赖。

生成两个文件：

  • test_msg.pbzero.h：包含所有消息类的完整定义，全部 inline。
  • test_msg.pbzero.cc：始终为空，仅为满足某些构建系统的规则假设。

每个生成的消息类还包含一个配套的 Decoder 类（继承自 TypedProtoDecoder），用于离线解析场景。序列化和反序列化使用不同的代码路径——这是 ProtoZero 与 libprotobuf 的设计分野之一。

字段写入方法

Section titled “字段写入方法”

Message 提供一组模板化的写入方法，每个方法都在栈上构造编码后的字节，然后通过 WriteToStream() 写入目标：

  • AppendVarInt(field_id, value)：编码 tag + varint 值。先写 MakeTagVarInt(field_id)，再写 value。适用于 int32、int64、uint32、uint64、bool、enum。
  • AppendSignedVarInt(field_id, value)：先 ZigZag 编码再调用 AppendVarInt。适用于 sint32、sint64。
  • AppendTinyVarInt(field_id, value)：对 0-127 的小数值优化，跳过 varint 循环，直接写一个字节。
  • AppendFixed(field_id, value)：编码 tag + 固定长度值（4 或 8 字节）。适用于 fixed32、fixed64、float、double。
  • AppendBytes(field_id, data, size)：编码 tag + 长度 varint + 原始字节。适用于 string、bytes。
  • AppendScatteredBytes(field_id, ranges, num_ranges)：从多个不连续的内存区域追加字节。

所有方法共享一个模式：在栈上的局部 buffer 中编码，然后调用 WriteToStream()。这个 buffer 的大小是 kMaxSimpleFieldEncodedSize = 15（5 字节 tag + 10 字节 varint），足够容纳任何非长度分隔字段的编码。

嵌套消息

Section titled “嵌套消息”

BeginNestedMessage<T>(field_id) 是 ProtoZero 处理嵌套消息的关键：

  1. 写入 field tag（标记这是一个 length-delimited 字段）。
  2. 通过 ReserveBytes(kMessageLengthFieldSize) 预留 4 字节给长度字段。
  3. 从 MessageArena 分配一个新的 Message 对象。
  4. 将新消息的 size_field_ 指向预留的 4 字节。
  5. 返回新消息的指针。

当父消息写入下一个字段或自身被 finalize 时，子消息自动被 finalize（通过 EndNestedMessage()）。这是隐式的——用户不需要手动关闭嵌套消息。

ScatteredStreamWriter：不连续缓冲区的写入引擎

Section titled “ScatteredStreamWriter：不连续缓冲区的写入引擎”

ProtoZero 的核心抽象是 ScatteredStreamWriter（include/perfetto/protozero/scattered_stream_writer.h）。它解决了 ProtoZero 面对的最基本问题：如何在不连续的内存片段中写入一个连续的字节流。

写入逻辑分两级：

Fast path——数据在当前 chunk 内部：

大多数写入走 fast path：一次 memcpy，推进 write_ptr_。成本与普通内存写入无异。

Slow path——数据跨越 chunk 边界：

WriteBytesSlowPath() 将写入拆分：先写满当前 chunk，然后调用 Delegate::GetNewBuffer() 获取新 chunk，继续写入剩余部分。在追踪场景中，GetNewBuffer() 会通过 SharedMemoryArbiter 获取一个新的共享内存 chunk，这涉及一次 mutex 锁操作。

关键设计假设：chunk 大小为 4-32 KB，两个线程同时跨越 chunk 边界的概率极低。因此 mutex 的竞争几乎为零，slow path 的成本被摊销到数千次 fast path 写入中。

ScatteredStreamWriter 的 Delegate 接口只有两个方法：

  • GetNewBuffer()：返回一个新的连续内存区域。
  • AnnotatePatch(patch_addr)：标记一个需要延迟修补的位置（后文详述）。

延迟 size 修补

Section titled “延迟 size 修补”

protobuf 的 length-delimited 字段（嵌套消息、string、bytes）在编码时需要在数据前面写入长度。但嵌套消息开始写入时，最终长度未知。

ProtoZero 的解决方案是 预留 + 延迟回填：

  1. BeginNestedMessage() 通过 ReserveBytes(4) 预留 4 字节。
  2. 子消息的所有字段写入完成后，Finalize() 回填实际大小到这 4 字节。

问题在于：4 字节的 varint 编码有多种合法表示。值 7 可以编码为 07（1 字节）或 87 80 80 00（4 字节）。ProtoZero 使用 冗余 varint 编码（WriteRedundantVarInt）：始终使用 4 字节，高位补 continuation bit。

标准 protobuf 解码器可以正确解析这种冗余编码——它们忽略高位的 continuation bit，只关心有效位。

小消息压缩

Section titled “小消息压缩”

预留 4 字节意味着每个嵌套层级都浪费 3 个字节。对于 Perfetto 的 trace 事件——通常很短——这个开销不可忽视。

Message::Finalize() 实现了一个压缩优化：当消息体足够小（≤ 127 字节）且 size_field_ 紧邻消息体在同一 chunk 内时，将 4 字节的冗余编码压缩为 1 字节的标准编码。具体步骤：

  1. 检查 size_ <= 127（1 字节 varint 的最大值）。
  2. 检查 size_field_ 是否就在 write_ptr_ - size_ - 4 的位置（即紧邻消息体前面）。
  3. 检查 size_field_ 在当前 chunk 内（不在已提交的旧 chunk 中）。
  4. 条件满足时：用 memmove 将消息体往前移动 3 字节，填补缩小的 gap；写入 1 字节 varint。

这个优化的效果：假设一个嵌套消息体 50 字节，不压缩时占 54 字节（4 字节冗余长度 + 50 字节内容），压缩后占 51 字节（1 字节标准长度 + 50 字节内容），节省 5.6%。在百万级 trace 事件的尺度上，这节省了可观的 trace 文件大小。

PatchList：跨 chunk 边界的修补

Section titled “PatchList：跨 chunk 边界的修补”

当嵌套消息跨越 chunk 边界时，压缩优化不再适用——size_field_ 可能在一个已提交的旧 chunk 中，无法直接回填。这是 PatchList 要解决的问题。

PatchList（src/tracing/core/patch_list.h）是一个由 std::forward_list<Patch> 支撑的容器。为什么用 forward_list 而不是 vector？因为 Message 持有指向 Patch::size_field 的原始指针——vector 的扩容会导致元素搬移，使这些指针失效。forward_list 的节点级指针稳定性正好满足需求。

工作流程：

  1. TraceWriterImpl::AnnotatePatch(patch_addr) 被调用（当一个嵌套消息的 size_field_ 落在 chunk 边界附近时）。
  2. 计算 size_field_ 在当前 chunk 中的偏移量，调用 patch_list_.emplace_back(chunk_id, offset)。
  3. 设置 chunk header 的 kChunkNeedsPatching 标志。
  4. 返回 &patch->size_field[0]，作为 Message 的 size_field_ 指针。
  5. 当 Message::Finalize() 运行时，实际的 varint 编码写入 patch->size_field。
  6. SharedMemoryArbiter 在发送 CommitDataRequest 时，将所有待处理的 patch 序列化到请求中。
  7. traced 在中央缓冲区中定位对应位置，写入 patch 携带的值。

这个机制的关键洞察：修补数据走 IPC 控制通道，不走共享内存。patch 的数据量很小（每个 Patch 结构体 10 字节：4 字节 ChunkID（uint32_t）+ 2 字节 offset + 4 字节 size_field，加上对齐填充为 12 字节），附带在 CommitDataRequest 中的开销可以忽略。

性能特征

Section titled “性能特征”

ProtoZero 的设计文档中包含了详尽的基准测试，对比了 ProtoZero、libprotobuf 和一个”光速序列化器”（假设所有边界检查和编码开销为零的理想情况）。

在 Google Pixel 3（aarch64）上的结果：

场景libprotobufProtoZero光速序列化器
简单事件402 ns242 ns118 ns
3 层嵌套事件1810 ns780 ns138 ns

简单事件 ProtoZero 比 libprotobuf 快 40%。嵌套事件快 57%。ProtoZero 的开销约为光速序列化器的 2 倍——考虑到它处理了 varint 编码、边界检查和不连续缓冲区管理，这是一个极好的结果。

嵌套场景的差距更大，原因在于：libprotobuf 的嵌套消息需要为每个子消息分配 RepeatedPtrField 中的对象，而 ProtoZero 从 arena 中分配，成本接近零。

安全约束

Section titled “安全约束”

ProtoZero 的 .pbzero.h 代码不依赖任何外部库——只使用 C++ 标准库。这对于 Tracing SDK 的可移植性至关重要：Perfetto 需要将整个追踪客户端代码打包为一个可嵌入的 SDK（amalgamation），不允许引入额外的依赖。

所有生成的方法都是 inline 的，编译器可以穿透所有层次的内联展开。这意味着一次 set_int_val(42) 调用在编译后可能只是几条 mov 指令加上一次 memcpy（或其内联等价物）。

本文小结

Section titled “本文小结”

ProtoZero 不是一个通用的 protobuf 库。它是为追踪写入路径量身定制的序列化引擎，通过 append-only 模式消除了中间存储，通过 ScatteredStreamWriter 直接写入不连续的共享内存 chunk，通过延迟 size 修补解决了嵌套消息的长度编码问题，通过压缩优化减少了小消息的编码开销。这些设计选择使得 Perfetto 的快速路径可以做到接近零开销的 protobuf 序列化。

下一篇，我们将深入 TraceWriter 的实现，看它如何将 ProtoZero 与共享内存仲裁器连接起来，完成从单个 trace 事件到共享内存 chunk 的完整数据流。
