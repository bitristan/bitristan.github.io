Perfetto （十五）：调度分析

从 sched_switch 到线程状态模型

Section titled “从 sched_switch 到线程状态模型”

Linux 内核的调度事件（sched_switch、sched_waking、sched_wakeup）是 trace 数据中最丰富也最复杂的部分。Perfetto 将这些原始事件转化为两个核心表——sched 和 thread_state——然后在其上构建调度延迟、关键路径、并行度等高级分析。

两个核心表

Section titled “两个核心表”

sched_slice_table（per-CPU 视角）

Section titled “sched_slice_table（per-CPU 视角）”

sched 表记录每个 CPU 上的调度切片：

列类型说明
tsTimestamp切片起始时间
durDuration持续时间（-1 表示未结束）
utidUtId线程 ID
end_stateString切片结束时的线程状态
priorityInt调度优先级
ucpuCpuIdCPU ID

SchedEventTracker（sched_event_tracker.h）是调度事件的核心处理器，提供 AddStartSlice()、ClosePendingSlice() 等操作方法，直接访问 sched_slice_table。FtraceSchedEventTracker（ftrace_sched_event_tracker.h）是 ftrace 专用的适配层，持有 SchedEventState 成员，提供 PushSchedSwitch()、PushSchedSwitchCompact()、PushSchedWakingCompact() 等 ftrace 事件解析方法。

thread_state_table（per-线程视角）

Section titled “thread_state_table（per-线程视角）”

thread_state 表记录每个线程经过的所有调度状态：

列类型说明
tsTimestamp状态起始时间
durDuration持续时间
utidUtId线程 ID
stateString状态码
io_waitBool是否是 IO 等待
blocked_functionString阻塞函数名
waker_utidUtId唤醒者线程
waker_idId唤醒者的 thread_state 行 ID（自引用）
irq_contextInt是否在 IRQ 上下文中被唤醒
ucpuCpuIdCPU ID

ThreadStateTracker（importers/common/thread_state_tracker.h）是状态机的核心。它维护 prev_row_numbers_for_thread_ 向量（按 utid 索引），记录每个线程最近的 open 行和 blocked 行。

线程状态分类

Section titled “线程状态分类”

Linux 内核用单字母编码线程状态。PerfettoSQL 的 sched_state_to_human_readable_string() 函数（stdlib/sched/states.sql）做翻译：

内核码Perfetto 名称含义
RunningRunning正在 CPU 上执行
RRunnable可运行，在等待 CPU
R+Runnable (Preempted)被抢占，仍在运行队列
SSleeping可中断睡眠（通常是等待事件）
DUninterruptible Sleep不可中断睡眠（通常是 IO）
TStopped被信号停止
tTraced被 ptrace 停止
XExit (Dead)已退出（最终状态）
ZExit (Zombie)僵尸进程（已退出但未被 wait）
xTask Dead任务已终止（内核内部）
IIdle内核线程空闲
KWakekill被 wakekill 信号唤醒
WWaking正在被唤醒的过程中
PParked停泊状态（CPU 热插拔相关）
NNo Load无负载标记

Windows ETW 还有额外的状态码：Waiting, Deferred Ready, Initialized, Stand By, Transition。

D 状态进一步区分 IO 等待：sched_state_io_to_human_readable_string() 根据 io_wait 标志附加 “(IO)” 或 “(non-IO)” 后缀。

调度延迟分析

Section titled “调度延迟分析”

sched_previous_runnable_on_thread

Section titled “sched_previous_runnable_on_thread”

stdlib/sched/runnable.sql 定义了一个关键视图：对于每个 “Running” 状态，找到它之前最近的 “Runnable” 状态——两者的时间差就是调度延迟（线程在运行队列中等待的时间）。

关键设计：

  • GLOB 'R*' 匹配所有以 R 开头的状态：'R'（Runnable）、'R+'（被抢占）和 'Running'。这是 state IN ('R', 'R+', 'Running') 的性能优化写法。
  • FILTER 子句区分普通 runnable 和有 waker 的 wakeup runnable。
  • irq_context != 1 排除 IRQ 上下文中的唤醒（不是真正的进程间依赖）。

概念

构建过程

Section titled “构建过程”
  1. _runnable_state：选取所有有唤醒者的非结束状态（dur != -1 AND waker_id IS NOT NULL），并标记阻塞类型（is_irq 列）。is_irq 的逻辑：IRQ 上下文唤醒时为 1，进程上下文中则取 io_wait 值（即 IO 等待也为 1）。is_irq 标记在下游 _wakeup_graph 中用于区分阻塞原因。
  2. _sleep_state：所有 S、D、I 状态。
  3. _wakeup：将每个 Runnable 与其前面的 Sleep 状态配对（S→R 对）。
  4. _wakeup_graph：使用窗口函数（LAG、LEAD）构建完整的 waker/prev 依赖关系。
  5. _critical_path_by_roots：调用 C++ 的 __intrinsic_critical_path_walk 执行关键路径图遍历。

关键路径

Section titled “关键路径”

关键路径回答的问题是：“这个线程为什么执行了这么久？谁阻塞了它？”

关键路径：A 被 B 阻塞 → B 被 C 阻塞 → … 直到找到一个在 CPU 上实际执行的线程。

__intrinsic_critical_path_walk 是一个 C++ 函数，它接收 wakeup 图的聚合数据和根节点数组，返回每一步的阻塞关系。结果是一个 (root_id, depth, ts, dur, blocker_id, blocker_utid, parent_id) 的 7 列序列。parent_id 标识上一层级的阻塞者（depth 0 时为 root_id），用于重建完整的阻塞链。

三种关键路径模式

Section titled “三种关键路径模式”
模式用途
_critical_path_by_roots从一组根节点出发，每个 (root_id, ts) 一个阻塞者
_critical_path_with_depth_by_roots保留链深度信息
_critical_path_by_intervals对特定时间区间（如应用启动）做分析

线程级并行度

Section titled “线程级并行度”

stdlib/sched/thread_level_parallelism.sql 通过 intervals_overlap_count 宏计算三个时间序列：

时间序列含义
sched_runnable_thread_count任意时刻有多少线程处于 Runnable 状态
sched_uninterruptible_sleep_thread_count任意时刻有多少线程处于 D 状态
sched_active_cpu_count任意时刻有多少 CPU 有非 idle 任务

这些指标直接反映系统负载：Runnable 线程数远大于 CPU 数说明 CPU 不足；D 状态线程数高说明 IO 瓶颈。

本文小结

Section titled “本文小结”

Perfetto 的调度分析从 ftrace 的 sched_switch 事件出发，构建了两个互补的表：per-CPU 的 sched 表和 per-线程的 thread_state 表。调度延迟分析通过窗口函数找到每次 Running 之前的 Runnable 状态。Thread executing span 和关键路径分析追踪完整的因果链——“谁阻塞了谁”——并支持生成 pprof 兼容的火焰图。状态分布和并行度分析提供了系统级的调度健康度视图。这些分析全部用 PerfettoSQL 实现，可以自由组合和扩展。
