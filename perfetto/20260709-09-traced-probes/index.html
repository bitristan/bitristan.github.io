Perfetto （九）：traced_probes

traced_probes 的角色

Section titled “traced_probes 的角色”

traced_probes 是一个独立的 Producer 进程，负责采集所有需要特权访问的系统数据：ftrace 内核事件、/proc 统计信息、电源状态、系统日志等。它不是单一功能的数据源，而是一个托管 20 个数据源的容器进程。

启动流程

Section titled “启动流程”

ProbesMain()（src/traced/probes/probes.cc）的启动步骤：

  1. 解析命令行参数（--background、--reset-ftrace、--cleanup-after-crash）。
  2. 创建单线程事件循环（base::MaybeLockFreeTaskRunner）。
  3. 创建 ProbesProducer 单例。
  4. 配置 Watchdog（内存和 CPU 限制）。
  5. 调用 producer.ConnectWithRetries(GetProducerSocket(), &task_runner) 连接到 traced。
  6. 进入事件循环：task_runner.Run()——永久阻塞，由 IPC 回调和定时器驱动。

ProbesProducer：核心协调者

Section titled “ProbesProducer：核心协调者”

ProbesProducer（src/traced/probes/probes_producer.h/.cc）继承 perfetto::Producer，同时实现 FtraceController::Observer。它是一个单例——整个进程只有一个 Producer 实例，所有数据源共享同一个 IPC 连接。

连接与注册

Section titled “连接与注册”

连接建立后，OnConnect() 遍历 kAllDataSources[]，为每个数据源生成 DataSourceDescriptor 并注册到 traced。注册分两轮进行：先生成所有 descriptor，再统一注册——避免 traced 看到半注册状态。

每个 descriptor 设置 will_notify_on_start(true) 和 will_notify_on_stop(true)，表示数据源支持 Start/Stop 回调。

数据源生命周期

Section titled “数据源生命周期”

SetupDataSource(instance_id, config)：

  1. 在 kAllDataSources[] 中查找 config.name()。
  2. 调用工厂函数创建数据源实例。
  3. 存入 data_sources_（拥有所有权）和 session_data_sources_（按会话+描述符分组的多值映射）。

StartDataSource(instance_id)：

  1. 标记 started = true。
  2. 调用 data_source->Start()。
  3. 通知 traced 已启动。
  4. 设置 watchdog 定时器（基于 trace_duration_ms + stop_timeout_ms）。

StopDataSource(id)：

  1. 销毁数据源实例。
  2. 从两个映射中移除。
  3. 通知 traced 已停止。

ProbesDataSource：数据源基类

Section titled “ProbesDataSource：数据源基类”

所有数据源继承 ProbesDataSource（src/traced/probes/probes_data_source.h）：

接口极其精简——只有三个虚函数。每个数据源类型有一个静态 descriptor 成员，包含名称和功能标志。

调度架构：自调度定时器

Section titled “调度架构：自调度定时器”

traced_probes 没有集中式调度器。每个轮询类数据源管理自己的定时器，使用 base::TaskRunner::PostDelayedTask()：

墙钟对齐（period_ms - (now_ms % period_ms)）确保 tick 在一致的绝对时间点触发，不受工作耗时的影响。所有数据源共享同一个单线程事件循环——定时器是交织的，不是真正并发的。如果一个数据源的 Tick() 耗时过长，会延迟其他所有数据源。

SysStatsDataSource：统一的 /proc 轮询

Section titled “SysStatsDataSource：统一的 /proc 轮询”

SysStatsDataSource（src/traced/probes/sys_stats/）是系统统计信息的统一采集器，注册为 "linux.sys_stats"。

最小兼容周期设计

Section titled “最小兼容周期设计”

SysStatsDataSource 不为每个 /proc 文件创建独立定时器。它使用单个主 tick 配合计数器除法：

主 tick 周期取所有启用周期的最小值（sys_stats_data_source.cc:183）。每个子计数器存储”每隔多少个主 tick 读取一次”。所有周期必须是最小周期的整数倍——如果某个周期不是整数倍，SysStatsDataSource 会打印错误日志并放弃初始化（PERFETTO_ELOG("SysStat periods are not integer multiples of each other")），不会进行取整。

ProcessStatsDataSource：进程级统计

Section titled “ProcessStatsDataSource：进程级统计”

ProcessStatsDataSource（src/traced/probes/ps/）注册为 "linux.process_stats"，支持两种并行运行的模式。

模式一：按需进程树转储

当 on_demand_dumps_enabled_ 为 true（默认）时，ftrace 的元数据回调将新发现的 PID 推送到此数据源：

这是 ftrace 与进程统计之间的推送式反馈循环：ftrace 发现新 PID → 触发 procfs 采集 → trace 数据更完整。

模式二：周期性统计轮询

Section titled “模式二：周期性统计轮询”

如果配置了 proc_stats_poll_ms，以该间隔遍历所有 /proc/<pid>/ 目录：

  • /proc/<pid>/status：VmSize、VmRSS、RssAnon、RssFile、RssShmem、VmSwap、VmLck、VmHWM。
  • /proc/<pid>/oom_score_adj。
  • /proc/<pid>/stat：用户态/内核态运行时间。
  • 可选：/proc/<pid>/smaps_rollup（PSS 详情）、/proc/<pid>/dmabuf_rss。

增量缓存：CachedProcessStats 存储每个计数器的上次写入值。只有变化的值才会写入 trace。缓存每 process_stats_cache_ttl_ticks_ 个 tick 清除一次。

Section titled “电源数据源”

AndroidPowerDataSource

Section titled “AndroidPowerDataSource”

注册为 "android.power"。通过动态加载的 libperfetto_android_internal.so 访问 Android Health HAL。采集四类数据：

  1. 电池计数器：电量、容量百分比、电流、电压。
  2. 电源轨：每个电源轨（CPU、GPU、屏幕）的能耗。
  3. 能耗估算：per-UID 的能耗分解。
  4. 实体状态驻留：SoC 电源状态的驻留时间。

ClearIncrementalState() 触发重新发射电源轨和能耗消费者描述符。

Section titled “LinuxPowerSysfsDataSource”

注册为 "linux.sysfs_power"。更简单的 Linux 替代方案——枚举 /sys/class/power_supply/ 读取电池信息。

Flush 协调

Section titled “Flush 协调”

当 traced 请求 Flush 时，ProbesProducer::Flush() 将 flush 扇出到所有已启动的数据源。通过 pending_flushes_ 跟踪待完成的 ack。所有数据源完成后调用 NotifyFlushComplete()。硬超时 kFlushTimeoutMs = 1000ms——超时后强制 ack。

MetatraceDataSource 有特殊处理：在 StopDataSource() 时优先 flush，以便捕获其他数据源的最终 flush 操作。

看门狗

Section titled “看门狗”

base::Watchdog 监控内存和 CPU 使用。watchdog 崩溃前，FlushForWatchdogAndCrash() 尝试 flush ftrace 数据源以辅助调试。每个数据源也有独立的 watchdog 定时器（基于 trace_duration_ms + stop_timeout_ms），检测卡住的数据源。

安全与隔离

Section titled “安全与隔离”

traced_probes 需要 root 权限或 CAP_SYS_ADMIN 能力来访问 /sys/kernel/tracing/ 和 /proc/<pid>/。它以降权方式运行——Android 上通过 init 的 capabilities 机制限制为最小权限集。

所有 20 个数据源共享同一个进程和 IPC 连接。如果 traced_probes 崩溃，所有数据源同时丢失——这是有意的设计选择。相比每个数据源一个进程的方案，单进程减少了进程数量和 IPC 开销，也简化了 Watchdog 的实现。

本文小结

Section titled “本文小结”

traced_probes 是一个精心设计的多数据源容器。20 个数据源通过编译时注册表统一管理，共享单线程事件循环和 IPC 连接。调度是去中心化的——每个数据源管理自己的定时器，墙钟对齐保证采样节奏。跨数据源的协调主要通过 ftrace 元数据的推送式回调实现。这种架构在简洁性和功能性之间取得了良好的平衡。
