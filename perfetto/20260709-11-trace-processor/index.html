Perfetto （十一）：Trace Processor

Trace Processor 的角色

Section titled “Trace Processor 的角色”

Trace Processor 是 Perfetto 的离线分析引擎。它消费原始 trace 数据（protobuf、Chrome JSON、systrace 等多种格式），将其解析为列式存储，然后通过 SQL 接口提供查询。它是 Perfetto UI 的后端，也是命令行分析工具的核心。

类层次结构

Section titled “类层次结构”

TraceProcessorImpl（src/trace_processor/trace_processor_impl.h）继承自两个基类：

  • TraceProcessor（公共 API）：提供 ExecuteQuery()、ComputeMetric()、RegisterSqlPackage() 等方法。
  • TraceProcessorStorageImpl：拥有解析管道——Parse(TraceBlobView)、Flush()、NotifyEndOfFile()。

这种分离使得存储/解析层独立于 SQL 引擎。

第一阶段：格式检测与分发

Section titled “第一阶段：格式检测与分发”

客户端反复调用 Parse(TraceBlobView) 推送原始数据。ForwardingTraceParser 在首次调用时：

  1. 调用 GuessTraceType() 从 magic bytes 自动检测 trace 格式。
  2. 从 TraceReaderRegistry 查找对应的 ChunkedTraceReader。

支持的格式：Perfetto proto、Chrome JSON、Systrace、Fuchsia、Gecko、perf.data、pprof、art_hprof、simpleperf、Android bugreport、gzip/tar/zip 容器等 15+ 种。

  1. 强制排序：OnPushDataToSorter() 强制排序器提取所有缓冲事件。

TraceSorter：全局时间序排序

Section titled “TraceSorter：全局时间序排序”

问题

Section titled “问题”

ftrace 事件按 per-CPU 缓冲区到达，不同 CPU 的事件交错无序。某些数据源的事件甚至可能大幅延迟到达。Trace Processor 需要按全局时间序处理所有事件。

架构

Section titled “架构”

TraceSorter（src/trace_processor/sorter/trace_sorter.h）实现了一个流式多路归并排序。它维护 N 个队列（N = CPU 数 + 1 个非 ftrace 事件队列），每个队列由 base::CircularQueue<TimestampedEvent> 支撑。

每个事件只是时间戳加上一个分配 ID。实际事件数据（TracePacketData、FtraceData 等）存储在 TraceTokenBuffer 中——一个基于 BumpAllocator（64 KB chunk）的高效内存池。

排序算法

Section titled “排序算法”

针对 ftrace 事件通常 per-CPU 有序的常见情况做了优化：

  1. 追加：事件追加到对应队列。如果新时间戳 ≥ max_ts_，队列保持有序。如果打破顺序，记录 sort_start_idx_ 和 sort_min_ts_。
  2. 排序：提取前，只对需要排序的队列的尾部 [sort_start_idx_, end] 使用 std::sort。用 std::lower_bound 在已排序前缀中找到精确起始位置。
  3. 提取：多队列归并——找到 min_ts_ 最小的队列，从中提取事件直到超过第二小队列的 min_ts_，然后重复。

Stream/Sink 模式

Section titled “Stream/Sink 模式”

格式特定的分词器获得 Stream<T> 句柄，调用 stream->Push(timestamp, data) 插入事件。另一端的 Sink<T>（由解析器实现）在事件按序提取时收到 Parse(timestamp, data) 回调。

TraceStorage：列式数据存储

Section titled “TraceStorage：列式数据存储”

TraceStorage（src/trace_processor/storage/trace_storage.h）是中心数据仓库，包含：

  • StringPool：字符串驻留系统。
  • 数十个类型化表：每个表由 Dataframe 支撑。

所有表存储在一个连续的对齐内存块中：

StringPool：字符串驻留

Section titled “StringPool：字符串驻留”

所有字符串在 StringPool 中驻留，系统其余部分通过 32 位 StringId 引用。

设计要点：

  • 小字符串（常见情况）存储在 4 MB 块中。32 位 ID 编码：[大字符串标志(1)] [块索引(9)] [块内偏移(22)]。
  • 大字符串（≥ 1 MB）单独存储，ID 的 MSB 置位。
  • FlatHashMap<uint64_t, Id, AlreadyHashed>（MurmurHash 作为哈希函数）实现去重。
  • Get(Id) 路径无锁，仅一次指针解引用。

表定义：代码生成

Section titled “表定义：代码生成”

表在 Python 文件中定义（src/trace_processor/tables/），通过代码生成产生 C++ 头文件。每个列指定名称、类型、访问标志、排序标志和 SQL 可见性名称。

Dataframe 作为虚拟表

Section titled “Dataframe 作为虚拟表”

DataframeModule（src/trace_processor/perfetto_sql/engine/dataframe_module.h）是 SQLite 虚拟表模块，桥接列式 Dataframe 存储和 SQLite：

  1. 每个表通过 CREATE VIRTUAL TABLE 注册。
  2. xBestIndex 将 SQLite 过滤约束翻译为 Dataframe 的 FilterSpec。
  3. Dataframe::PlanQuery() 生成优化的执行计划（字节码）。
  4. Dataframe::Cursor 迭代结果，将单元格翻译回 SQLite 值。

关键优化：表查询不是逐行通过 SQLite 评估的。SQLite 的虚拟表接口将 filter/sort/limit 约束下推到 Dataframe 自有的查询引擎，使用字节码驱动的列式评估。

PerfettoSQL

Section titled “PerfettoSQL”

PerfettoSQL 是 SQLite 的超集，扩展了以下语法：

INCLUDE PERFETTO MODULE：从注册的包中导入 SQL 模块。模块按域组织（android.binder、sched.runnable、slices.with_context 等）。

CREATE PERFETTO TABLE：创建由 Dataframe 支撑的物化表。

CREATE PERFETTO FUNCTION：定义 SQL 函数。支持 DELEGATE TO C++ 实现。

CREATE PERFETTO INDEX：在表上创建索引。

CREATE PERFETTO MACRO：参数化 SQL 片段（编译期文本替换）。

标准库

Section titled “标准库”

位于 src/trace_processor/perfetto_sql/stdlib/，25+ 个模块按域组织：android/、sched/、slices/、counters/、callstacks/、time/、intervals/、wattson/ 等。

注册的 C++ 函数

Section titled “注册的 C++ 函数”

通过插件系统注册的 C++ 函数包括：ancestor/descendant（树遍历）、span_join_operator（时间区间连接）、experimental_flamegraph（火焰图）、interval_intersect（区间交集）、graph_traversal（图遍历）、counter_intervals（计数器区间）、to_ftrace（回转 ftrace 格式）等。

插件系统

Section titled “插件系统”

TraceProcessorImpl 构造函数注册 50+ 个插件。每个 Plugin<> 子类可以：

  • 注册导入器到 TraceReaderRegistry。
  • 注册 Dataframe（列式表）。
  • 注册 SQLite 函数/模块/聚合函数。
  • 注册 proto 导入器模块和 track event 扩展。

插件在静态初始化时通过 GetPluginSet() 按依赖拓扑排序。

TraceProcessorContext：解析状态的生命周期

Section titled “TraceProcessorContext：解析状态的生命周期”

TraceProcessorContext 是拥有所有解析状态的”上帝对象”。它有精密的分叉模型：

  • 全局状态：跨所有 trace/机器共享（TraceStorage、TraceSorter、ClockSynchronizer）。
  • Per-trace 状态：每个被解析的文件独立（content_analyzer、trace_state）。
  • Per-machine 状态：每个虚拟机独立（ProcessTracker、CpuTracker、SymbolTracker）。
  • Per-trace-and-machine 状态：（ClockTracker、SliceTracker、TrackTracker）。

当归档中有多个文件时，通过 ForkContextForTrace() 分叉上下文——所有分叉共享全局状态，但有独立的 per-trace/per-machine 追踪器。

本文小结

Section titled “本文小结”

Trace Processor 是一个从多格式 trace 数据到 SQL 查询的完整管道。格式检测和多 reader 支持使其能处理 15+ 种 trace 格式。TraceSorter 的流式归并排序处理跨 CPU 的乱序事件。Dataframe 列式存储配合 StringPool 驻留最小化内存占用。SQLite 虚拟表接口将列式存储暴露为 SQL 可查询的表，同时通过约束下推和字节码执行绕过 SQLite 的逐行引擎。插件系统和 PerfettoSQL 标准库使得分析能力可以模块化扩展。

后续几篇文章将深入 TraceSorter、Dataframe 和 PerfettoSQL 的实现细节。
