深入 ftrace 与 fentry：从函数追踪器到高效入口钩子

关键词：Linux、ftrace、fentry、fentry、mcount、动态插桩、BPF trampoline、eBPF 适合人群：已读过 tracepoint / kprobe / fentry 系列，想从”原理”层面弄清楚 ftrace 到底是什么、它的局限在哪、fentry 又是如何改进它的读者。

摘要

Section titled “摘要”
  • ftrace（Function Tracer）是 Linux 内核内置的追踪框架，是 tracefs（/sys/kernel/tracing）的引擎，也是 tracepoint / kprobe / perf 等很多观测能力的底座。
  • 实现原理：编译器给每个内核函数开头插一条 call mcount（老）或 call __fentry__（新）；ftrace 在启动时把这些调用点全部 patch 成 nop（关闭≈零开销），启用时再 patch 成 call ftrace_caller，由它把事件写入 per-CPU 无锁 ring buffer。
  • mcount 方案的缺点：调用桩插在函数序言之后，进入时参数寄存器可能已被破坏 → 拿不到函数参数；桩必须保守地保存全部寄存器，开销偏大；通用路径对”只想挂个回调”来说偏重。
  • fentry 是 ftrace 埋桩的升级：gcc -mfentry 把 __fentry__ 插到函数最开头（序言之前），参数寄存器完好、栈未建，从而能读参数、开销更低。
  • fentry 的具体实现：__fentry__ 站点同样由动态 ftrace 管理（nop ↔ 直接调用）；eBPF 借 ftrace 的 direct call 把这个站点直接指向 BPF trampoline，trampoline 依据 BTF 知道函数签名，把参数以强类型传给你的 fentry/fexit 程序。

1. ftrace 是什么

Section titled “1. ftrace 是什么”

ftrace（Function Tracer）是 Linux 内核自带的追踪框架，由 Steven Rostedt 主导开发。它最初的目标很简单：弄清楚”内核里哪些函数被调用了、按什么顺序、花了多久”。但随着演进，它成了 Linux 可观测性最重要的底座之一。

它提供的能力大致有：

能力说明
function tracer记录每个被追踪函数的调用（函数地址 + 调用者 + 时间戳）
function_graph tracer记录调用关系图，并测出每个函数的耗时
dynamic ftrace运行时只追踪你选定的函数，而不是全部（关键优化）
event tracingtracepoint / trace event 的输出也走 ftrace 的 ring buffer
集成 kprobe / perf / eBPF这些机制的许多输出都汇聚到同一个 tracefs 界面

你平时在 /sys/kernel/tracing/ 下看到的 current_tracer、available_tracers、set_ftrace_filter、trace、events/ 等，全都是 ftrace 的用户接口（tracefs）。可以说：tracepoint、kprobe、uprobe、perf 解决”在哪埋点/怎么触发”，而 ftrace 解决”触发后记录到哪里、怎么呈现”。

2. ftrace 的实现原理

Section titled “2. ftrace 的实现原理”

ftrace 最精妙的地方在于：它能在”几乎零开销”和”全量函数追踪”之间自由切换。这靠三层机制实现。

2.1 第一层：编译器埋桩（-pg / -mfentry）

Section titled “2.1 第一层：编译器埋桩（-pg / -mfentry）”

ftrace 不是运行时去”找函数插桩”的，而是编译内核时，gcc 就在每个函数的开头插了一条调用桩：

  • 早期：-pg → 每个函数开头是 call mcount
  • 现代：-pg -mfentry → 每个函数开头是 call __fentry__

这条 call 的目标（mcount 或 fentry）在没启用追踪时是个”空 stub”（基本就是直接返回）。所有调用点的位置会被编译器收集到一个特殊段里（如 __mcount_loc），供内核启动时读取。

2.2 第二层：动态 ftrace（nop ↔ call 的运行时切换）

Section titled “2.2 第二层：动态 ftrace（nop ↔ call 的运行时切换）”

这是 ftrace 性能的关键。启动时 ftrace_init() 做一件事：把记录下来的每一个调用桩指令，全部 patch 成一条 nop（x86 上是 5 字节 nopl）。于是：

  • 追踪关闭时：每个函数开头的调用桩就是一条 nop，CPU 原样走过，几乎零开销。
  • 追踪开启时：ftrace 只把”你要追踪的那几个函数”的调用桩 patch 成 call ftrace_caller（一条相对调用指令），其他函数维持 nop。

修改正在运行的代码需要停止相关 CPU（x86 上借助 INT3 安全的 text_poke 机制），所以 patch 是”原子”完成的，不会让别的 CPU 读到半截指令。

2.3 第三层：ftrace_caller 与无锁 ring buffer

Section titled “2.3 第三层：ftrace_caller 与无锁 ring buffer”

当某个函数被启用追踪后，CPU 执行到它的调用桩就跳进 ftrace_caller：

  1. 保存当前寄存器现场；
  2. 调用当前注册的 tracer（如 function_trace_call）；
  3. tracer 把一条记录 <调用者 IP, 当前函数 IP, 时间戳> 写入 per-CPU 无锁 ring buffer（这是 ftrace 自带的 trace_buffer，专为高并发写入优化）；
  4. 恢复寄存器，返回，原函数继续。

读取端（cat trace）只是从 ring buffer 消费这些记录并格式化输出。整个过程不阻塞、不分配、不抢锁（per-CPU），所以即便高频函数被追踪，系统也不会被拖垮太多。

2.4 function_graph：用返回钩子测耗时

Section titled “2.4 function_graph：用返回钩子测耗时”

function_graph tracer 还想测”每个函数花了多久、调了谁”。它的做法是给被追踪函数额外挂钩返回地址——把栈上的返回地址替换成 ftrace 的 return_to_handler（类似 kretprobe 的 trampoline）。函数返回时先跳到 return_to_handler，记录耗时和调用关系，再跳回真正的返回地址。这样就能画出调用图。

3. ftrace 的缺点（准确说，是 mcount 方案的局限）

Section titled “3. ftrace 的缺点（准确说，是 mcount 方案的局限）”

ftrace 框架本身很成功，但它早期的埋桩方式（mcount）有结构性短板。这些短板正是后来 fentry(fentry) 出现的直接原因。

3.1 调用桩插在”函数序言之后” → 拿不到函数参数

Section titled “3.1 调用桩插在”函数序言之后” → 拿不到函数参数”

-pg 让 gcc 在函数序言（prologue）之后才插入 call mcount。问题在于，函数序言通常会：建立栈帧（push %rbp; mov %rsp,%rbp）、把参数寄存器 spill 到栈上、甚至可能改动参数寄存器。等 CPU 真正进入 mcount 时，原始的调用约定参数寄存器（di/si/dx/cx/r8/r9）已经不再可靠地保留着函数参数。

结果就是：mcount 能告诉你”这个函数被调用了、是谁调用的”，但很难拿到函数被调用时的参数（比如 do_sys_open 的 filename）。对追踪/可观测来说，拿不到参数往往意味着价值大打折扣。

3.2 桩必须保守地保存全部寄存器 → 开销偏大

Section titled “3.2 桩必须保守地保存全部寄存器 → 开销偏大”

因为 mcount/ftrace_caller 不知道上层 tracer 到底要什么，为了安全，它一进来就把几乎所有寄存器都保存一遍。这对”我只是想看一眼某个参数”的场景来说，是一笔不小的固定税——每个被追踪的函数调用都得付。

3.3 调用约定尴尬、可移植性差

Section titled “3.3 调用约定尴尬、可移植性差”

在部分架构上，mcount 是通过某个特定寄存器（如返回地址放在 %rax）来传递上下文的，实现繁琐、架构相关性强，给移植和维护带来负担。

3.4 通用路径对”只想挂个回调”偏重

Section titled “3.4 通用路径对”只想挂个回调”偏重”

即便你只是想”函数 X 被调用时跑一下我的回调”，mcount 路径也要走：ftrace_caller → 通用 tracer 分发 → ring buffer 写入。这条通用链路对 eBPF 这类”要一个快、直接的钩子”的需求来说太重了——你并不总想把每条记录都写进 ring buffer。

小结：mcount 方案的根因是”埋桩位置太晚（序言之后）+ 通用路径太重”。只要把埋桩提前到函数最开头，并给”直接调用你的回调”开一条快路径，这些问题就迎刃而解。

4. 引出 fentry

Section titled “4. 引出 fentry”

解法就是 gcc 的 -mfentry（GCC 4.6 引入）：

  • 它把调用桩从”序言之后”挪到了函数的第一条指令——即 call __fentry__，早于任何栈帧建立和寄存器改动。
  • 于是进入 __fentry__ 时，调用约定里的参数寄存器（di/si/dx/cx/r8/r9）原封不动，可以直接读到函数参数。
  • 同时，因为桩在更早起的位置、桩本身要做的寄存器保存也更少，整体开销比 mcount 低。
  • 内核自较早期（x86 约 3.x 起）就逐步把默认函数桩从 mcount 换成了 __fentry__，现代内核基本默认使用 fentry 机制。

注意一个容易混淆的点：fentry 不是”替代 ftrace 的新框架”，而是 ftrace 埋桩方式的升级。它仍然走 ftrace 的动态 patch 机制（nop ↔ call），只是桩从 mcount 换成了 __fentry__，位置更靠前。

而让 fentry 在 eBPF 圈真正发光的关键一步是：Linux 5.5 起，内核允许把 __fentry__ 站点直接”短路”调用到自定义 trampoline（ftrace 的 direct call），eBPF 借此把 BPF 程序挂了上去——这就是你前面在 SEC("fentry/func") / SEC("fexit/func") 里看到的。

5. fentry 的具体实现原理

Section titled “5. fentry 的具体实现原理”

把 fentry 拆成”埋桩 → 动态 patch → direct call → BPF trampoline”四步看就清楚了。

5.1 埋桩：fentry 在函数最开头

Section titled “5.1 埋桩：fentry 在函数最开头”

和 mcount 一样，__fentry__ 也是编译器插入的调用桩，只是位置在最开头。默认情况下 __fentry__ 是个 weak 空 stub。

5.2 动态 patch：和 ftrace 共用同一套机制

Section titled “5.2 动态 patch：和 ftrace 共用同一套机制”

__fentry__ 站点同样被 ftrace 在启动时收集、全部 patch 成 nop：

  • 关闭：nop，零开销。
  • 启用：patch 成 call <handler>。

到这一步，fentry 和普通 ftrace 其实是同一条路——区别仅在桩的位置（更靠前、能拿参数）。

5.3 关键升级：ftrace direct call（给 BPF 的快路径）

Section titled “5.3 关键升级：ftrace direct call（给 BPF 的快路径）”

普通 ftrace 启用时，站点 patch 到 ftrace_caller（通用路径：保存全寄存器 → tracer → ring buffer）。但内核还提供 direct call 能力：允许把一个 ftrace 站点直接 patch 成 call <你的 trampoline>，绕开 ftrace_caller 的通用分发。

5.4 BPF trampoline 做什么

Section titled “5.4 BPF trampoline 做什么”

trampoline 是 fentry 体验”又好又快”的核心：

  • 对于 fentry（入口）：trampoline 按当前架构的调用约定，把函数的参数（寄存器/栈上）收集起来；因为它通过 BTF 知道 do_sys_open 的真实签名，就能把这些参数以强类型传给你的 BPF 程序。验证器（verifier）会用 BTF 校验你的程序参数类型与函数签名一致——所以你能直接写：

  • 对于 fexit（返回）：trampoline 还会保存返回地址和参数，函数返回时再次进入 trampoline，把返回值（以及上下文）交给你的 fexit 程序。

5.5 为什么既快又有类型

Section titled “5.5 为什么既快又有类型”
  • 快：__fentry__ 在入口、nop↔直接调用、且直接 call 到 BPF trampoline，没有 int3 断点、没有单步、没有 ftrace_caller 的通用分发和全寄存器保存。
  • 有类型：强类型来自 BTF——trampoline 和 verifier 都按 BTF 里的函数签名工作，参数”按名、按类型”直接可用。

6. 一张图看清几者的关系

Section titled “6. 一张图看清几者的关系”
方案埋桩位置能否拿参数路径/开销典型用途
ftrace（mcount）序言之后不可靠ftrace_caller 通用路径，较重函数流/调用图（不关心参数）
ftrace（fentry/fentry）函数最开头能ftrace_caller 通用路径同上，但能读参数、更轻
kprobe任意指令（换 int3）寄存器读（pt_regs）断点+单步，中灵活挂任意指令
fentry（eBPF）函数最开头（fentry）强类型参数（BTF）direct call → BPF trampoline，低函数级高效追踪（推荐）

一句话：fentry 就是”ftrace 的 fentry 埋桩 + direct call 快路径 + BPF trampoline + BTF 类型”的组合体。ftrace 负责底座，fentry 负责把底座用到极致。

7. 总结

Section titled “7. 总结”
  • ftrace 是内核可观测性的底座：靠编译器埋桩 + 动态 patch（nop↔call）+ per-CPU ring buffer，做到”关闭零开销、开启可追踪”。
  • mcount 方案的缺点是埋桩太晚（序言之后，拿不到参数）、桩保守保存全寄存器（开销大）、通用路径偏重——这些根因催生了改进。
  • fentry（fentry）把埋桩提前到函数最开头，参数寄存器完好、开销更低；它仍是 ftrace 机制的一部分，而非替代品。
  • fentry 的具体实现 = __fentry__ 站点由动态 ftrace 管理 + ftrace direct call 把它指向 BPF trampoline + trampoline 依 BTF 以强类型参数调用你的 fentry/fexit 程序。于是你得到”快 + 能拿参数 + 类型安全”的函数钩子。

理解了 ftrace 与 fentry 的底层，再回头看 tracepoint / kprobe / fentry 三篇就会明白：它们本质上是**不同”埋桩哲学”**在可观测性上的体现——静态埋点（tracepoint）、动态断点（kprobe）、以及 ftrace 进化出的高效入口钩子（fentry）。
