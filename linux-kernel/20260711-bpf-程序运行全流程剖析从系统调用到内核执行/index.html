从系统调用到内核执行：BPF 程序运行全流程剖析

摘要

Section titled “摘要”

BPF（Berkeley Packet Filter）已从最初的网络包过滤框架演变为 Linux 内核的可编程基础设施。本文以一个统计进程切换次数的 raw tracepoint 程序为例，自顶向下追踪 BPF 程序从用户态编写、编译、加载、验证、JIT 编译，到最终在内核事件触发时执行的完整过程。所有分析基于 Linux 内核源码（v6.x），文中引用的源码路径均可对照查阅。

1. 引言

Section titled “1. 引言”

1.1 BPF 是什么

Section titled “1.1 BPF 是什么”

eBPF（extended BPF）允许用户态程序将经过验证的安全字节码注入内核，在内核事件（如网络包到达、tracepoint 命中、系统调用发生）触发时执行。与内核模块（LKM）相比，BPF 程序经过验证器的严格安全检查，不会导致内核崩溃；与 kprobe 等动态追踪机制相比，BPF 程序可以经 JIT 编译为本机指令，性能接近原生代码。

1.2 本文目标

Section titled “1.2 本文目标”

许多 BPF 教程侧重于”怎么用”（libbpf API、BCC 工具），而较少深入”内核到底怎么处理”这一层面。本文聚焦于一个核心问题：

当用户态调用 bpf(BPF_PROG_LOAD, ...) 后，内核内部究竟发生了什么？BPF 字节码最终是如何变成内核中可执行代码的？

1.3 适用读者

Section titled “1.3 适用读者”
  • 了解 BPF 基本概念，希望深入理解内核实现机制的工程师
  • 熟悉 Linux 内核开发基本概念（系统调用、tracepoint、内核数据结构）
  • 具备 C 语言阅读能力

3.2 bpf_prog_load() 的六个步骤

Section titled “3.2 bpf_prog_load() 的六个步骤”

bpf_prog_load() 是加载流程的核心函数（kernel/bpf/syscall.c:2864），其工作可分为六步：

步骤一：权限与参数校验

Section titled “步骤一：权限与参数校验”

检查项包括：CAP_BPF 权限、指令数上限、attach 类型合法性、程序类型与权限的匹配（如 perf 事件类程序需要 CAP_PERFMON）。

步骤二：分配 struct bpf_prog 并拷贝字节码

Section titled “步骤二：分配 struct bpf_prog 并拷贝字节码”

struct bpf_prog 是内核中表示一个 BPF 程序的核心数据结构，其 insns 字段指向从用户态拷入的 BPF 字节码。

步骤三：关联程序类型操作表

Section titled “步骤三：关联程序类型操作表”

此调用根据 prog_type 将 prog->aux->ops 设为对应的操作表（如 raw_tracepoint_prog_ops）。操作表定义了该类型程序可以调用哪些 helper 函数、可以访问哪些上下文字段等。

步骤四：验证器——安全检查的核心

Section titled “步骤四：验证器——安全检查的核心”

bpf_check() 是 BPF 子系统安全性的根基（kernel/bpf/verifier.c:19915）。它对字节码进行模拟执行（而非真正执行），检查以下方面：

  1. 控制流安全：程序不能有无限循环；所有向后跳转必须有数学上可证明的有限上界
  2. 寄存器类型追踪：验证器维护每个寄存器在每条指令处的类型状态（标量、指向 map 的指针、指向栈的指针、ctx 指针等），确保不会解引用非法地址
  3. helper 函数白名单：程序类型决定可调用的 helper 子集。raw tracepoint 程序可以调用 bpf_map_lookup_elem，但不能调用 bpf_xdp_adjust_head 等 XDP 专用 helper
  4. 内存访问边界：所有指针解引用必须落在验证器已确认的安全范围内
  5. 复杂度限制：指令总数、指令验证数（含分支展开）、调用深度均有上限

验证器对程序的所有可达路径进行状态空间探索。对于本例的 count_switch，验证器会确认：

  • bpf_map_lookup_elem 返回值可能是 NULL 或有效指针，两条路径都安全
  • __sync_fetch_and_add 访问的地址来自 map，且在 map 值大小范围内
  • 程序必定在有限指令内执行 BPF_EXIT

注意：验证器通过后，会在 bpf_check() 内部（kernel/bpf/verifier.c:20189）调用 __bpf_prog_select_runtime()，进入 JIT 编译阶段。这意味着验证和 JIT 在同一次 bpf_check() 调用中完成。

步骤五：JIT 编译

Section titled “步骤五：JIT 编译”

__bpf_prog_select_runtime()（kernel/bpf/core.c:2601）决定程序的执行方式：

bpf_int_jit_compile() 是架构相关函数。在 x86_64 上（arch/x86/net/bpf_jit_comp.c），它将 BPF 字节码翻译为 x86_64 本机指令。以本例中的几条指令为例：

BPF 字节码JIT 后的 x86_64 指令（示意）
BPF_MOV64_IMM(R1, 0)xor eax, eax
BPF_STX_MEM(W, R10, R1, -4)mov DWORD PTR [rbp-4], eax
BPF_MOV64_REG(R2, R10)mov rsi, rbp
BPF_ALU64_IMM(ADD, R2, -4)add rsi, -4
BPF_LD_MAP_FD(R1, map)mov edi, <map_ptr>
BPF_EMIT_CALL(map_lookup_elem)call __bpf_map_lookup_elem
BPF_JMP_IMM(JEQ, R0, 0, off)test rax, rax; je <exit>
BPF_EXIT_INSN()ret

JIT 完成后：

  • prog->bpf_func 被设为本机代码入口地址
  • prog->jited 设为 1

如果 JIT 不可用或失败（且未设置 CONFIG_BPF_JIT_ALWAYS_ON），prog->bpf_func 会回退到解释器入口 ___bpf_prog_run（kernel/bpf/core.c:1786），该函数使用 GCC computed goto 跳转表逐条解释 BPF 指令。

8.1 三阶段生命周期

Section titled “8.1 三阶段生命周期”

阶段触发方执行次数关键操作

执行内核事件触发多次bpf_func() 被调用

8.2 验证器是安全根基

Section titled “8.2 验证器是安全根基”

BPF 程序能安全地直接在内核上下文执行，根本原因在于验证器在加载时已排除了所有危险行为。验证器通过后，内核无需在执行时再做安全检查——这也是 BPF 性能接近原生代码的前提。

8.3 JIT 消除解释开销

Section titled “8.3 JIT 消除解释开销”

JIT 将 BPF 字节码编译为本机指令后，执行时只是一个普通的函数调用（通过 prog->bpf_func 函数指针）。没有解释器的逐条译码开销，也没有虚拟机的上下文切换。

8.4 统一的执行入口

Section titled “8.4 统一的执行入口”

无论程序是 JIT 执行还是解释执行，调用入口都是 bpf_prog_run(prog, ctx) → prog->bpf_func(ctx, insns)。这个统一的函数指针抽象使事件触发侧的代码无需关心执行方式。

9. 总结

Section titled “9. 总结”

本文以一个统计进程切换次数的 raw tracepoint BPF 程序为例，完整追踪了从用户态 bpf() 系统调用到内核事件触发的执行全流程：

  1. 编译：用户态 C 代码经 clang 编译为 BPF 字节码
  2. 加载：BPF_PROG_LOAD 系统调用进入内核，经权限检查、字节码拷贝、程序类型关联后，由验证器 bpf_check() 进行模拟执行安全验证，验证通过后触发 JIT 编译将字节码转为本机指令
  3. Attach：BPF_RAW_TRACEPOINT_OPEN 将程序通过 tracepoint 框架的 probe 机制挂载到目标 tracepoint，启用 static_branch
  4. 执行：tracepoint 事件触发时，经 __bpf_trace_##call → bpf_trace_runN → __bpf_trace_run → bpf_prog_run 调用链，最终执行 prog->bpf_func 指向的 JIT 代码
  5. 读取：用户态通过 BPF_MAP_LOOKUP_ELEM 读取 map 中的结果

BPF 的核心设计哲学是：用加载时的验证开销换取运行时的零安全检查，用 JIT 编译消除解释开销，用统一的函数指针抽象屏蔽执行方式差异。这使得 BPF 程序既能保证内核安全，又能达到接近原生代码的执行性能。
