Linux 时间子系统演进（四）：动态 tick 与功耗优化

聚焦版本：Linux 2.6.21 - 3.x

1. 问题：周期 tick 的代价

Section titled “1. 问题：周期 tick 的代价”

在 hrtimer + clocksource + clockevent 框架建立之后，Linux 已经能够精确到纳秒级定时。但有一个基础假设没有改变：

无论 CPU 忙不忙，每个 CPU 都按固定频率 HZ 接收时钟中断。

这意味着：

  • 一个 8 核服务器，每秒产生 8 × 250 = 2000 次 tick 中断。
  • 笔记本电脑空闲时，CPU 每秒仍被唤醒 250 次，无法进入深睡眠。
  • 实时任务即使不需要调度，也会被周期 tick 打断。

NO_HZ（tickless）的目标就是：把周期 tick 改成按需触发。当 CPU 空闲且没有定时器到期时，干脆停止 tick。

2. 关键前提：oneshot clockevent

Section titled “2. 关键前提：oneshot clockevent”

动态 tick 之所以能实现，是因为 2.6 引入了支持单次触发（oneshot）的 clockevent 设备。周期模式下，硬件自动每隔 1/HZ 产生一次中断；oneshot 模式下，每次中断后必须由软件重新编程下一次中断时间。

有了 oneshot，内核就可以把下一次中断设为”下一个需要处理的事件”，而不是机械的 1/HZ。

3. NO_HZ_IDLE：空闲时停止 tick

Section titled “3. NO_HZ_IDLE：空闲时停止 tick”

3.1 核心思想

Section titled “3.1 核心思想”

CONFIG_NO_HZ_IDLE（旧称 CONFIG_NO_HZ）让 CPU 在进入 idle 时停止周期 tick。内核会检查：

  1. 是否有 timer_list 定时器即将到期？
  2. 是否有 hrtimer 到期？
  3. 是否需要更新 jiffies？
  4. RCU、负载计算等是否依赖 tick？

如果都没有近期的 tick 需求，就把 clockevent 编程到下一个真正需要唤醒的时刻，然后让 CPU 进入深睡眠。

3.2 状态转换

Section titled “3.2 状态转换”

3.3 关键数据结构：tick_sched

Section titled “3.3 关键数据结构：tick_sched”

每个 CPU 有一个 struct tick_sched 记录当前的 tick 状态：

tick_sched 中关键的字段包括：

  • flags：当前 tick 状态标志，如 TS_FLAG_STOPPED（tick 已停止）、TS_FLAG_NOHZ（NO_HZ 启用）、TS_FLAG_HIGHRES（高分辨率模式）。
  • next_timer：下一个将要到期的定时器时间（主要用于调试/信息展示，见 tick-sched.h 注释）。
  • check_clocks：标记是否需要重新检查 clocksource 变化。

3.4 进入和退出 idle 的路径

Section titled “3.4 进入和退出 idle 的路径”

注：tick_nohz_idle_exit() 不直接调用 scheduler_tick()；它调用 tick_nohz_idle_update_tick() 决定恢复周期 tick 还是继续 tickless，scheduler_tick() 在后续的 tick 中断路径上触发。在 NO_HZ_FULL 模式下，退出 idle 时更倾向于继续保持 tickless，相关调度与记账工作常通过 hrtimer、IPI 等按需完成。

3.5 jiffies 怎么办

Section titled “3.5 jiffies 怎么办”

jiffies 仍然需要推进，即使 CPU 在睡觉。Linux 的做法是：

  • 内核用 tick_do_timer_cpu 指定唯一负责调用 do_timer() 的 CPU。当该 CPU 进入 NO_HZ 空闲时，会把职责标记为 TICK_DO_TIMER_NONE，由下一个参与 timekeeping 的 CPU 接管。
  • 负责 CPU 在醒来时一次性把 jiffies 推进多个 tick；tick_do_update_jiffies64() 会根据当前时间和 last_jiffies_update 的差值，计算需要推进多少 jiffies。

这样即使 CPU 睡了数秒，jiffies 也不会掉队。

4. dynticks：更彻底的动态化

Section titled “4. dynticks：更彻底的动态化”

4.1 从”关闭 tick”到”按需 tick”

Section titled “4.1 从”关闭 tick”到”按需 tick””

NO_HZ_IDLE 让空闲 CPU 停止 tick。dynticks（dynamic ticks）是实现这一能力的底层机制：它把 tick 设备从周期模式切换到单次触发（oneshot）模式，使 tick 变成按需触发的动态事件。

在 dynticks 模式下，进入 idle 前内核会计算”下一个需要处理的事情”，然后把 clockevent 编程到那个时刻。tick 不再是”固定节拍”，而是按需发生。需要注意的是，2.6/3.x 时代的 dynticks 主要作用于 idle CPU；在 CPU 忙碌或有任务运行时，周期 tick 仍然存在。让运行中的 CPU 也停止 tick 是后续 NO_HZ_FULL 的工作。

4.2 tick 设备的状态机

Section titled “4.2 tick 设备的状态机”

4.3 tick_nohz_next_event

Section titled “4.3 tick_nohz_next_event”

在 oneshot 模式下，tick 调度器需要回答一个问题：下一次 tick 应该什么时候发生？

它会综合以下信息：

  • 下一个 timer_list 定时器。
  • 下一个 hrtimer。
  • 下一个 jiffies 更新点。
  • RCU 的 quiescent state 检查点。
  • 负载统计采样点。

然后取最小值，调用 tick_program_event() 把 clockevent 编程到那个时刻。

5. tick-broadcast：多核同时空闲怎么办

Section titled “5. tick-broadcast：多核同时空闲怎么办”

5.1 问题

Section titled “5.1 问题”

现代 CPU 有 C-states。最深的 C-state 下，某些 CPU 的本地 per-CPU timer（如 Local APIC Timer）可能停止工作（CLOCK_EVT_FEAT_C3STOP）。当某个 CPU 的本地 timer 在深睡眠下不可用时，谁来唤醒它？

5.2 解决方案

Section titled “5.2 解决方案”

引入一个全局的、低功耗的广播时钟设备（broadcast clock），通常是 PIT 或 HPET。当某个 CPU 发现自己的本地 timer 在深睡眠下不可用时，就把下一个唤醒任务委托给 broadcast 设备。

5.3 工作流程

Section titled “5.3 工作流程”

tick-broadcast 是 NO_HZ 在多核平台上真正可用的关键。

6. sched_clock：统一的调度时间戳

Section titled “6. sched_clock：统一的调度时间戳”

6.1 为什么需要

Section titled “6.1 为什么需要”

调度器、tracing、perf、lockdep 都需要一个快速、单调、架构无关的纳秒时间戳。2.6 早期 sched_clock() 由架构各自实现，有的基于 TSC，有的基于 jiffies，导致：

  • 不同架构行为不一致。
  • TSC 不稳定时 sched_clock 可能回退。
  • 32 位系统上 TSC 回绕问题严重。

6.2 通用 sched_clock 框架

Section titled “6.2 通用 sched_clock 框架”

3.x（3.11 左右）kernel/time/sched_clock.c 完成跨架构通用化：

架构注册一个低层读函数 read_sched_clock()，框架负责：

  • 周期性地扩展 epoch，把 32/64 位 cycle 计数扩展为 64 位 ns。
  • 使用 seqcount_latch 实现无锁读。
  • 同 CPU 上单调；跨 CPU 比较在迁移、虚拟化等场景下仍需谨慎。

7. 优点总结

Section titled “7. 优点总结”
  1. 空闲功耗显著降低：笔记本 idle 时不再每秒被唤醒 250 次，电池续航大幅提升。
  2. 数据中心节能：大量 CPU 空闲时，中断风暴消失。
  3. OS jitter 降低：周期 tick 不再是固定噪声源，实时和 HPC 受益。
  4. 多核扩展性增强：tick-broadcast 让深睡眠成为可能。
  5. sched_clock 统一：调度器和性能工具获得跨架构一致的纳秒时间戳。

8. 局限与代价

Section titled “8. 局限与代价”

8.1 唤醒延迟增加

Section titled “8.1 唤醒延迟增加”

从 idle 深睡眠中醒来需要恢复时钟、退出 tickless 状态，路径比周期 tick 更长。对极端实时场景，这可能不可接受。

8.2 时间记账变复杂

Section titled “8.2 时间记账变复杂”

jiffies、utime/stime、负载统计都依赖 tick。tick 不均匀后，必须显式计算”睡了多久”，一次性补账。

8.3 调试困难

Section titled “8.3 调试困难”

以前 jiffies 均匀增长，现在可能一次跳多下。printk 时间戳、perf 采样、lockup watchdog 都要适应非均匀 tick。

8.4 仍不能解决单任务场景

Section titled “8.4 仍不能解决单任务场景”

NO_HZ_IDLE 只处理空闲 CPU。如果 CPU 上只有一个任务在运行，周期 tick 仍然每隔几毫秒打断它。这是 NO_HZ_FULL 要解决的问题。

9. 向现代 timekeeping 过渡

Section titled “9. 向现代 timekeeping 过渡”

动态 tick 时代把”周期 tick”变成了”按需 tick”，但它仍然默认每个可运行 CPU 都需要 tick。下一阶段的思路更激进：

如果 CPU 上只有一个可运行任务，那也不需要周期 tick。

这就是 NO_HZ_FULL。它要求：

  • 用户任务不被 tick 打断。
  • 所有内核记账、RCU、调度检查都通过其他机制（如 hrtimer、IPI）完成。
  • 对时间戳读取的速度要求更高，因此需要 vDSO。

同时，容器和虚拟化的兴起也对时间子系统提出新的要求：多个容器能否拥有独立的时间线？用户态能否不通过 syscall 快速读时？这些问题将在 4.x 及以后的版本中得到回答。

10. 小结

Section titled “10. 小结”

Linux 2.6.21 到 3.x 是时间子系统从”高精度”走向”按需触发”的时代。NO_HZ_IDLE 让空闲 CPU 停止周期 tick；dynticks 把 tick 变成动态事件；tick-broadcast 解决了多核深睡眠的唤醒问题；sched_clock 提供了统一的调度时间戳。这些改进大幅降低了功耗和 OS jitter，但也带来了更复杂的时间记账和调试挑战。它们共同为 4.x 时代的 NO_HZ_FULL、vDSO、time namespace 等更激进的特性铺平了道路。
