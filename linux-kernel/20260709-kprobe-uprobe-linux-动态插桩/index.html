深入 Linux 内核 kprobe 与 uprobe：动态插桩的两把手术刀

关键词：Linux、kprobe、kretprobe、uprobe、uretprobe、eBPF、动态插桩、可观测性 适合人群：已了解 tracepoint，想补齐”内核/用户态任意位置动态追踪”能力的 eBPF 学习者。

摘要

Section titled “摘要”
  • kprobe 是内核态动态插桩：运行时把目标函数某条指令换成断点（int3），命中后再恢复执行。tracepoint 没覆盖的地方靠它。
  • kretprobe 是 kprobe 的”返回版”：把函数返回地址换成 trampoline，函数返回时先跑你的逻辑。
  • uprobe / uretprobe 是用户态版的 kprobe：基于二进制文件（inode），所有运行该程序的进程共享同一个探针。
  • eBPF 挂载：SEC("kprobe/func") / SEC("kretprobe/func") / SEC("uprobe/PATH:sym") / SEC("uretprobe/PATH:sym")，上下文都是 struct pt_regs *，参数要从寄存器里读（用 PT_REGS_PARMx）。
  • 现代替代：fentry / fexit 基于 BTF，比 kprobe 更快、更稳定，新内核优先用它挂函数。

1. 引子：tracepoint 的”盲区”

Section titled “1. 引子：tracepoint 的”盲区””

上一篇讲了 tracepoint：内核里预先埋好的静态钩子，有现成就用，稳、快。但它有个硬限制——只有内核作者提前埋点的地方才能追。

现实里你常常会碰到：

  • 想追一个内部静态函数，但它没暴露 tracepoint；
  • 想追某个内核函数返回时的值（比如 do_sys_open 返回了哪个 fd）；
  • 想追用户态程序里的函数，比如 bash 里用户输入的命令、某个 Go/Python 服务的内部调用。

这些 tracepoint 都帮不上。这时候需要动态插桩——运行时把探针”钉”到任意函数的任意指令上。内核给了两把手术刀：kprobe（内核态） 和 uprobe（用户态）。

2. kprobe / kretprobe：内核态动态插桩

Section titled “2. kprobe / kretprobe：内核态动态插桩”

2.1 概念

Section titled “2.1 概念”

kprobe 允许你在几乎任意内核函数的入口（或函数内任意偏移的指令）插入一个探针，不修改内核源码、不重新编译、不重启。

它怎么做到”运行中插入”？核心是把目标位置的那条机器指令临时替换成一个断点（x86 上是 int3）：

命中流程（简化）：

  1. 你 register_kprobe()，内核把目标地址的指令换成 int3（或经优化换成 jmp，见下文 optprobe）。
  2. CPU 执行到那里触发断点，陷入内核，保存现场到 struct pt_regs。
  3. 调用你的 handler。
  4. 单步执行被替换掉的那条原指令，再恢复现场、继续原流程。

kretprobe 则换了个思路：它不盯入口，而是把函数栈上的返回地址替换成一段 trampoline。函数执行完 ret 时先跳到 trampoline，跑你的逻辑，再跳回真正的返回地址。这样你能在函数”出口”拿到返回值。

2.2 性能与优化

Section titled “2.2 性能与优化”
  • 基础实现靠 int3 软断点 + 单步，有开销，不适合最热路径狂打。
  • 现代内核有两层优化：
    • optprobe（优化 kprobe）：当条件安全（函数未被内联、不在黑名单等）时，用一条 jmp 直接跳到探针桩，省掉单步，开销大幅下降。
    • ftrace-backed kprobe：若函数本身带 fentry/mcount 桩（大多数函数都编译了），kprobe 可以复用 ftrace 机制而不是 int3，更快。
  • kprobe 黑名单：kprobe 自身依赖的代码路径（如 kprobe_handler 相关函数）、以及部分极敏感函数不能被 kprobe，内核维护了一份 blacklist（/sys/kernel/debug/kprobes/blacklist）。

2.3 限制

Section titled “2.3 限制”
  • 内联函数挂不上：被内联展开的函数没有独立地址，kprobe 找不到”函数入口”；即便用 objdump 找到某条指令偏移，也只覆盖那一处展开点。
  • 不能保证多版本一致：函数名/符号会随内核版本变化，kprobe 比 tracepoint 更”脆”。

3. uprobe / uretprobe：用户态动态插桩

Section titled “3. uprobe / uretprobe：用户态动态插桩”

3.1 概念

Section titled “3.1 概念”

uprobe 是 kprobe 的用户态孪生兄弟：把探针钉到某个用户态二进制（可执行文件 / 共享库）里的函数或指令上。

关键设计：uprobe 是基于文件的（inode），不是基于进程的。你在一个二进制（如 /bin/bash）上注册 uprobe 后，所有映射到这个文件的进程都会自动获得这个探针——新启动的进程也包含。这点和 kprobe 基于内核符号异曲同工，但作用域在用户空间。

3.2 机制

Section titled “3.2 机制”

uprobe 由内核的 uprobes 子系统管理，但”断点”是落在被追踪进程的地址空间里的：

  1. 你在文件偏移（或符号）处注册 uprobe，内核在对应 inode 记录探针。
  2. 当进程执行到该地址，指令已被替换为 int3（x86），触发该进程的断点。
  3. 陷入内核，保存 pt_regs，调用你的 handler；随后单步原指令、恢复。
  4. uretprobe 同理用 trampoline 处理函数返回（常见用法：在 readline 返回处拿到用户输入的命令字符串）。

3.3 限制

Section titled “3.3 限制”
  • 需要二进制里带有符号表（或被 perf/bpf 通过其他方式解析出地址）；strip 过的二进制要指定偏移或借助补充信息。
  • 用户态指针要用 bpf_probe_read_user_* 读，不能用内核指针的 helper。

6. 踩坑与最佳实践

Section titled “6. 踩坑与最佳实践”
  1. 内联函数别硬挂 kprobe：找不到函数入口。先 cat /proc/kallsyms | grep <func> 确认符号存在；不存在就用上层可导出的函数，或换 fentry/tracepoint。
  2. 参数要从寄存器正确读取：kprobe/uprobe 的 ctx 是 pt_regs，别像 tracepoint 那样直接 .字段名。x86-64 用 PT_REGS_PARMx，架构相关宏在 bpf_tracing.h。
  3. 用户态指针用 bpf_probe_read_user_*：在 uprobe 里读用户内存（如 bash 命令字符串）必须走 user 系列 helper，否则 verifier 拒绝。
  4. 返回值得用 ret 版本：想拿返回值，挂 kretprobe/uretprobe/fexit，用 PT_REGS_RC(ctx)（kprobe/uprobe 入口处还拿不到返回）。
  5. 性能与黑名单：kprobe 比 tracepoint 慢一截（断点/单步），热路径慎用；避开 /sys/kernel/debug/kprobes/blacklist 里的函数。
  6. strip 过的二进制：uprobe 需要能定位符号/偏移，对 strip 过的文件要提供偏移或补充调试信息。
  7. 跨版本脆弱：kprobe/uprobe 依赖符号名或二进制布局，内核/程序升级后要回归测试。

7. 总结

Section titled “7. 总结”

kprobe/uprobe 把”动态插桩”能力补全到 tracepoint 覆盖不到的地方：

  • kprobe/kretprobe 让你钉进任意内核函数的入口或返回，是 tracepoint 的灵活兜底（新内核上 fentry 是更优解）。
  • uprobe/uretprobe 把同一套能力带到用户态程序，一个二进制注册、所有进程共享。
  • 三者的交集是：eBPF 都能挂，但 kprobe/uprobe 的上下文是 pt_regs，参数要从寄存器读——这是和 tracepoint”结构化字段”最直观的区别。

学到这里，你的”事件源工具箱”已经凑齐了：tracepoint（静态）、kprobe/fentry（内核动态）、uprobe（用户动态）。下一步该深入的是不管挂哪种事件都通用的那套机制——Verifier、Maps、BTF/CO-RE、Helper，以及 libbpf 工程化。
