深入 Linux 内核 Tracepoint：一行埋点，如何做到默认零开销、按需极低代价

关键词：Linux 内核、tracepoint、trace event、eBPF、可观测性、jump label 适合人群：对内核可观测性、eBPF 感兴趣，想搞清楚 sched:sched_switch、syscalls:sys_enter_openat 这些事件到底从哪来的开发者。

摘要

Section titled “摘要”
  • tracepoint 是内核源码里预先留好的静态钩子，默认”关闭”，运行时挂上探针（probe）才生效。
  • 它”关闭时几乎零开销”的秘密是 jump label（静态键）：禁用时那段调用被直接 patch 成 NOP，不是运行时 if 判断。
  • 内核里你看到的 subsys:event（如 sched:sched_switch）本质上是 TRACE_EVENT 宏 定义出的 tracepoint + trace event，并以目录形式暴露到 /sys/kernel/tracing/events/。
  • eBPF 可以挂到 tracepoint 上：SEC("tp/...") 拿到结构化的事件上下文，SEC("raw_tp/...") 拿到原始参数、性能更高。
  • 选型口诀：有现成 tracepoint 优先用 tracepoint；要追到函数内部才上 kprobe。

1. 引子：你想”看见”内核，但又不能动它

Section titled “1. 引子：你想”看见”内核，但又不能动它”

设想一个场景：你的服务在生产环境偶发延迟尖刺，你怀疑是某些系统调用或上下文切换在作怪。你想知道内核在那一刻到底在干什么——但不能重启机器、不能改内核代码、最好也别装内核模块（生产环境你懂的）。

这正是 Linux 可观测性要解决的问题。内核给你准备了好几层”内窥镜”：

层次机制一句话
静态埋点tracepoint / trace event源码里预先留好的钩子
动态插桩kprobe / uprobe运行时挂到任意函数/指令
采样perf_events / PMU周期性看 CPU 在干嘛
函数追踪ftrace内核内置的函数调用追踪器

本文主角 tracepoint，是其中最”廉价、稳定、生产可用”的一类，也是 eBPF 程序挂载的首选事件源之一。理解了它，你再看 bpftool、perf、bpftrace、BCC 里那一长串事件名，就不会觉得是黑魔法了。

2. 什么是 Tracepoint

Section titled “2. 什么是 Tracepoint”

一句话：

tracepoint 是内核代码中预先放置的轻量级钩子。编译期就存在，但默认不做事；只有当运行时把你的探针函数挂上来，它才在那个代码路径上调用你。

它的几个关键属性：

  • 静态：位置写死在源码里（不像 kprobe 可以随便挂到任意地址）。
  • 近乎零开销（关闭时）：没挂探针时几乎不消耗任何东西。
  • 可传任意参数：埋点时声明了原型，调用处可以把 task_struct *、pid_t 等上下文传给探针。
  • 可多探针共存：同一个 tracepoint 可以同时挂 ftrace、perf、eBPF 的探针。

一个 tracepoint 由”两半”组成：

  1. 声明（declaration）：放在头文件，定义”这个事件长什么样”（参数原型）。
  2. 定义 + 触发（definition + call site）：放在 .c 文件，真正在代码路径上调用 trace_xxx()。

3.2 TRACE_EVENT：你日常遇到的其实是它

Section titled “3.2 TRACE_EVENT：你日常遇到的其实是它”

直接写 DECLARE_TRACE 比较原始。内核里 99% 的 tracepoint 是用 TRACE_EVENT 宏定义的——它是 DECLARE_TRACE 的高层封装，一次性帮你完成：

  1. 声明 tracepoint；
  2. 生成 trace event 的 format（字段布局），从而暴露到 /sys/kernel/tracing/events/；
  3. 生成把参数序列化成 ring buffer 记录的代码。

结论：你以用户态看到的 subsys:event（如 sched:sched_switch） = 一个 TRACE_EVENT 定义出的 tracepoint（钩子） + trace event（用户态可观测化身）。

Section titled “3.3 为什么关闭时几乎零开销：jump label”

这是灵魂。触发点的逻辑（简化后）等价于：

__DO_TRACE 会 rcu_dereference 出 funcs 数组，然后依次调用每个探针。关键在于 static_key_false：

  • 默认（无探针）时，这个 static_key 处于某个状态，对应分支被内核的 jump label 机制直接 patch 成一条 NOP / 不跳转指令。
  • 一旦你 register_trace_* 挂上第一个探针，key 被翻转，内核 把那段指令重新 patch 成真正去调用探针数组的代码。

也就是说，tracepoint 的”开关”不是在运行时判断 if (enabled)，而是在机器码层面把整段调用插入/移除。所以”关闭的 tracepoint”即使在调度器、系统调用入口这种最热的路径上，也几乎不影响性能——这正是内核敢在高频路径上埋大量 tracepoint 的原因。

3.4 多探针、类型安全与模块卸载

Section titled “3.4 多探针、类型安全与模块卸载”
  • 同一个 tracepoint 可挂多个探针（ftrace、perf、eBPF 可同时生效）。
  • 参数类型在 register_trace_* 时由编译器校验（探针函数指针类型必须与 TP_PROTO 匹配），因此传参是类型安全的。
  • 模块卸载前务必调用 tracepoint_synchronize_unregister() 确保没有 CPU 还在跑旧探针；配合”探针调用期间禁用抢占”的约定，保证卸载安全。

libbpf 把 tracepoint 分成两类。

(a) 普通 tracepoint —— SEC("tp/subsys/event")

上下文是该 trace event 的结构体（与 format 布局一致，由 vmlinux.h 里的 trace_event_raw_* 生成）。字段可直接按名访问，最直观。

(b) 原始 tracepoint —— SEC("raw_tp/event")

Section titled “(b) 原始 tracepoint —— SEC("raw_tp/event")”

上下文是 struct bpf_raw_tracepoint_args，里面是该 tracepoint 原始的 TP_PROTO 参数数组 args[]，不经过 trace event 的序列化，性能更高，但需自己知道参数顺序。

(c) 两者怎么选

Section titled “(c) 两者怎么选”
维度tp/（TRACEPOINT）raw_tp/（RAW_TRACEPOINT）
上下文trace event 结构体（与 format 一致）原始 TP_PROTO 参数数组 args[]
性能有 trace event 封装/序列化开销更低：直接拿到原始参数
字段访问通过 vmlinux.h 生成的 trace_event_raw_* 结构体，按名访问通过 ctx->args[i] 下标，需自己知道顺序
适用入门、想直接读 event 字段高频路径、追求极致性能

经验法则：先用 tp/ 把逻辑跑通，确认在热路径上成为瓶颈后再换 raw_tp/。

6. Tracepoint vs Kprobe：选型

Section titled “6. Tracepoint vs Kprobe：选型”
维度tracepointkprobe
类型静态埋点（编译期插入）动态插桩（运行时改指令为 trap）
禁用时开销几乎为零（jump label patch 成 NOP）目标地址被改指令，需恢复（现代内核有 optprobe 优化）
稳定性来源依赖 tracepoint 名字（版本间可能变，但一般比函数名稳定）依赖函数符号名（函数改名/内联/后缀变化就失效）
启用时性能高略低（trap/单步/优化路径有成本）
是否需要调试信息否（名字即可）通常需要符号表 / BTF
拿参数方式通过 trace event 结构或 raw 参数通过 pt_regs 寄存器布局解析
挂载灵活度仅限已埋点的地方几乎任意内核函数 / 指令

一句话选型：有现成 tracepoint → 用它（稳定、便宜、字段清楚）；要追的地方没埋点，或要追到函数内部某条指令 → kprobe / kretprobe；高频路径追求极致 → raw tracepoint。

7. 踩坑与最佳实践

Section titled “7. 踩坑与最佳实践”
  1. tracepoint 不是内核 ABI 保证。虽然 events/ 下事件相对稳定，但内核仍可能改名、改字段。raw_tp 尤其脆弱（依赖 TP_PROTO 参数顺序），大版本升级要回归测试。
  2. 字段访问用 CO-RE（vmlinux.h + bpf_core_read），避免不同内核版本结构体偏移不一致导致 verifier 拒绝或读错。
  3. 用户态指针用 bpf_probe_read_user_*，内核态用 bpf_probe_read_kernel_*，混用会被 verifier 拦下。
  4. 热路径上的 BPF 程序要轻。tracepoint 在调度/系统调用入口极频繁，重逻辑会让整体系统变慢——用 map 聚合，把”重活”留到用户态。
  5. 生产环境关注 buffer 丢数据：perf/ring buffer 满会丢事件，map 大小要预估。
  6. bpf_printk 仅用于调试，生产请用 perf/ring buffer + 自定义事件，别刷 trace_pipe。

8. 总结

Section titled “8. 总结”

tracepoint 用”编译期埋钩子 + jump label 运行时插拔”的设计，做到了”默认零成本、按需极低开销”的可观测性基础设施。它以 TRACE_EVENT 形式暴露成 tracefs 里的 subsys:event，既能让 ftrace/perf 直接消费，也是 eBPF 挂载的核心事件源。

对你做 eBPF 可观测性来说，掌握 tracepoint 意味着：知道哪些事件”现成可用”（不用一上来就 kprobe 硬刚）、理解 tp/ 与 raw_tp/ 的取舍、能对照 format 文件正确构造 BPF 上下文结构体。
