Linux 时间子系统演进（二）：jiffies 与固定 tick 时代

聚焦版本：Linux 0.01 - 2.4

1. 时代背景

Section titled “1. 时代背景”

1991 年发布的 Linux 0.01 运行在最原始的 IBM PC 兼容机上。那时的时间子系统只需要做三件事：

  1. 让内核知道”过去了多久”。
  2. 让内核能在未来某个时刻执行回调。
  3. 维护一个 wall-clock（墙上时钟），供文件时间戳和 time() 使用。

这三个任务被统一到一个非常简洁的模型里：由硬件定时器以固定频率产生中断，每次中断推进全局计数器 jiffies，并顺便检查所有需要执行的内核定时器。这个模型一直沿用到 Linux 2.4，成为后来一切时间子系统的起点。

2. 核心数据结构与全局变量

Section titled “2. 核心数据结构与全局变量”

2.1 HZ 与 jiffies

Section titled “2.1 HZ 与 jiffies”

HZ 是内核编译时确定的每秒 tick 数。早期 x86 上 HZ 通常为 100，即每 10ms 一次时钟中断。

jiffies 是一个全局 32 位（后来 64 位）无符号计数器，记录系统启动以来发生的 tick 次数。

注：jiffies 在 32 位系统上存在回绕问题。64 位版本 jiffies_64 在后续开发版本（2.5.x）中引入，用于需要长周期计量的场景。

2.2 xtime：墙上时间

Section titled “2.2 xtime：墙上时间”

墙上时间（wall time）保存在 struct timeval xtime 中，由 tick 中断在每个 tick 上加一个固定增量来维护。

每次 tick 中断会调用 do_timer()，其中把 jiffies 加一，并把 xtime 增加 1/HZ 秒。用户态的 gettimeofday() 最终读取 xtime 加上当前 tick 周期内由硬件定时器计数算出的微秒级偏移。

3. 定时器轮（Timer Wheel）

Section titled “3. 定时器轮（Timer Wheel）”

为了在海量定时器中快速找到到期的定时器，Linux 采用了经典的”定时器轮”结构。可以把轮盘理解成一个哈希桶数组，桶的下标对应 jiffies 的低若干位。

当 jiffies 增加时，只需要查看当前索引对应的桶，把其中到期的定时器取出执行。插入时根据 expires - jiffies 的差值决定放到哪一级轮盘，从而实现接近 O(1) 的添加和删除。

注：上图是单级简化示意。Linux 2.4/2.6 的实际实现是 TVR/TVN 多级级联定时器轮，通过逐级 cascade 处理长周期定时器。

定时器轮在处理网络超时、块设备延迟操作等毫秒级场景时非常高效；但它天然以 jiffies 为单位，精度不可能超过 1/HZ。

4. tick 中断的处理流程

Section titled “4. tick 中断的处理流程”

4.1 硬件触发

Section titled “4.1 硬件触发”

在 x86 上，8253/8254 PIT 通常被配置为模式 3（方波模式），每 1193182 / HZ 个 PIT 时钟周期就向 8259 PIC 发送一次 IRQ0。（部分场景或早期代码也使用模式 2 速率发生器。）

4.2 软件处理链

Section titled “4.2 软件处理链”

do_timer() 是架构无关的核心，负责推进时间；update_process_times() 负责与进程相关的 tick 工作，比如减少当前进程的时间片、触发 scheduler_tick()、执行当前 CPU 到期的定时器。

5. 架构耦合问题

Section titled “5. 架构耦合问题”

在这个时代，每个架构都需要自己实现类似下面的代码：

  • 初始化 PIT/RTC/架构相关定时器。
  • 提供 timer_interrupt()。
  • 在启动时从 RTC 读取初始时间填入 xtime。
  • 实现 do_gettimeofday() 读取 xtime。

例如 x86 有 arch/i386/kernel/time.c，ARM、MIPS、PowerPC 等各自有一套。时间子系统与硬件细节强耦合，新增一个架构或新的时钟源都要修改多处文件。

6. 优点总结

Section titled “6. 优点总结”
  1. 实现简单：全局一个计数器、一个中断、一个定时器轮，容易理解和维护。
  2. 开销可预测：tick 频率固定，每次 tick 的工作量基本固定。
  3. 调度与时间自然同步：每次 tick 都检查调度，时间推进和任务切换天然绑定。
  4. 网络栈友好：TCP 超时、重传等以 jiffies 为单位的粗粒度定时器，在 timer wheel 上效率很高。

7. 缺点与瓶颈

Section titled “7. 缺点与瓶颈”

7.1 精度受限

Section titled “7.1 精度受限”

所有时间相关操作都以 jiffies 为单位，典型精度 10ms。即使把 HZ 提高到 1000，精度也只能到 1ms，而且中断开销会显著增加。

对于多媒体同步、工业控制、高精度采样等场景，10ms 乃至 1ms 都远远不够。

7.2 空闲功耗高

Section titled “7.2 空闲功耗高”

CPU 进入空闲状态后，tick 中断依然每秒触发 100 次，每次都要从 C-state 浅睡眠中醒来。对笔记本电脑和嵌入式设备来说，这会显著缩短电池续航。

7.3 实时性差

Section titled “7.3 实时性差”

timer_list 定时器只能在 tick 边界处理，高优先级实时任务无法被精确唤醒。

7.4 架构耦合严重

Section titled “7.4 架构耦合严重”

新的时钟硬件、新的架构都需要修改架构相关代码，难以统一维护。

8. 向下一时代过渡的动因

Section titled “8. 向下一时代过渡的动因”

到 Linux 2.4 末期，社区已经清楚地认识到：

  • 必须有一个与 jiffies 无关的纳秒级时间基线。
  • 必须抽象时钟硬件，把架构相关代码压缩到最小。
  • 必须允许按需触发中断，而不是无条件地每秒 100/250/1000 次。

这三个诉求分别对应了下一时代的三大核心机制：hrtimer、clocksource/clockevent 和 NO_HZ/tickless。

9. 小结

Section titled “9. 小结”

jiffies 时代奠定了 Linux 时间子系统的基本形态：tick 驱动、jiffies 计数、timer_list 超时。它简单、可靠，支撑了 Linux 前十年的发展，但也因为精度、功耗和架构耦合问题，成为后续重构的对象。理解这一时代的数据结构和处理流程，是理解 hrtimer、clocksource、NO_HZ 等现代机制的前提。
